## 13.1 Três perguntas antes de confiar

O AutoML entrega um modelo pronto em poucos minutos. Isso é uma vantagem enorme, mas traz um risco: **é fácil usar um modelo que ninguém entende**. Antes de colocar qualquer modelo para decidir algo que afete pessoas, três perguntas devem ser respondidas.

![f13_perguntas](Figura 13.1 — As três perguntas antes de confiar em um modelo: eu o entendo? ele é justo? quanto ele custa?)

1. **Eu entendo o que ele faz?** (explicabilidade)
2. **Ele trata as pessoas de forma justa?** (ética e equidade)
3. **Quanto ele custa, e o que ele não consegue fazer?** (custo e limites)

:::cotidiano Analogia: o piloto automático
O piloto automático de um avião é uma maravilha, mas **o comandante precisa saber o que ele faz**, quando ele falha e quando assumir o controle. O AutoML é um piloto automático para modelos: não elimina a responsabilidade humana, só a desloca.
:::

## 13.2 Explicabilidade

### 13.2.1 Interpretável ou explicado depois?

Há duas maneiras de lidar com a "caixa-preta".

- **Modelos interpretáveis por construção:** um modelo cuja lógica pode ser lida diretamente (regressão logística com poucos coeficientes, árvore pequena, regras).
- **Explicações pós-hoc:** ferramentas que, **depois** do treino, tentam explicar um modelo complexo (importância de atributos, SHAP, LIME).

Rudin (2019) defende que, em decisões de **alto risco** (saúde, crédito, justiça), deve-se **preferir modelos interpretáveis** em vez de explicar caixas-pretas, porque explicações pós-hoc **podem ser imprecisas** e não revelam o que o modelo realmente computa. E há um achado prático importante: com frequência, o modelo interpretável **não perde** em desempenho. Vamos testar isso no conjunto **Breast Cancer Wisconsin** (UCI), comparando uma regressão logística com um boosting, por validação cruzada de 10 partes.

```python
import warnings; warnings.filterwarnings("ignore")
import numpy as np
from sklearn.datasets import load_breast_cancer
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import cross_val_score, StratifiedKFold
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler

X, y = load_breast_cancer(return_X_y=True)
cv = StratifiedKFold(10, shuffle=True, random_state=0)
lr = make_pipeline(StandardScaler(), LogisticRegression(C=0.5, max_iter=3000))
hgb = HistGradientBoostingClassifier(random_state=0)
for nome, m in (("Regressão logística (interpretável)", lr), ("Boosting (caixa-preta)", hgb)):
    s = cross_val_score(m, X, y, cv=cv)
    print(f"{nome:<38s} acurácia = {s.mean():.3f} (desvio {s.std():.3f})")
```
```saída
Regressão logística (interpretável)    acurácia = 0.981 (desvio 0.020)
Boosting (caixa-preta)                 acurácia = 0.968 (desvio 0.022)
```

As duas notas ficam **muito próximas** (0,981 contra 0,968, com desvios de cerca de 0,02): a diferença está dentro da variação entre partes e, aqui, até favorece o modelo simples. Em um problema como esse, a regressão logística entrega o desempenho do boosting com a vantagem de ser **legível**. O AutoML, ao buscar só pela métrica, pode escolher a caixa-preta mesmo quando um modelo simples basta; por isso vale **incluir modelos interpretáveis no espaço de busca** e preferi-los em caso de empate técnico.

:::dica Dica: a regra do empate técnico
Se um modelo simples e um complexo diferem **menos que a variação entre divisões**, escolha o simples. Você ganha explicação, velocidade e menos risco.
:::

### 13.2.2 Explicação global e local

![f13_explicacao](Figura 13.2 — Explicações globais (o modelo como um todo) e locais (uma decisão específica).)

- **Explicação global:** responde "**o que o modelo valoriza em geral?**" (por exemplo, a importância de cada atributo).
- **Explicação local:** responde "**por que o modelo decidiu isso para esta pessoa?**".

Para praticar, vamos criar um problema de **concessão de crédito simulado**. Usaremos dados **sintéticos**, para que possamos conhecer a **verdade que, no mundo real, nunca conhecemos**. Há 6.000 pessoas, em dois grupos: o grupo 0 (70%) e o grupo 1 (30%, "minoritário"). Cada pessoa tem uma **capacidade real de pagamento** (uma variável escondida), e os atributos observados são: **renda**, **tempo de emprego**, **razão de dívida**, **score histórico** e um **CEP-score** (que, como acontece na vida real, é um pouco **correlacionado com o grupo**). A renda do grupo 1 é, em média, um pouco menor, por razões estruturais.

O ponto-chave: os **rótulos de treino** são as **decisões históricas de crédito**, que foram **enviesadas contra o grupo 1** (a aprovação exigia mais dessas pessoas). Como simulamos tudo, também sabemos **quem de fato pagaria**.

Antes do código, uma decisão de protocolo que vale para todo o capítulo. Dividimos as 6.000 pessoas em **três partes**: **treino** (3.150 pessoas, onde o modelo aprende), **validação** (1.050, usada para **calibrar probabilidades e escolher limiares de decisão**) e **teste** (1.800, usado **só para medir**, com as regras já congeladas). Isso é o mesmo protocolo dos Capítulos 2 e 4: quem escolhe não pode ser quem mede.

```python
import warnings; warnings.filterwarnings("ignore")
import json
import numpy as np
from sklearn.model_selection import train_test_split

r = np.random.default_rng(0); n = 6000
g = (r.random(n) < 0.3).astype(int)                          # 1 = grupo minoritário
z = r.normal(0, 1, n)                                        # capacidade real de pagamento (escondida)
renda = np.exp(0.5 * z + 0.35 * r.normal(size=n) - 0.25 * g) * 3.0
emprego = np.clip(5 + 2 * z + r.normal(0, 2, n), 0, None)
divida = np.clip(0.4 - 0.1 * z + r.normal(0, 0.1, n), 0, 1)
cep = 0.8 * g + 0.6 * r.normal(size=n)                       # variável proxy do grupo
score = z + r.normal(0, 1, n)
y_real = (z > 0).astype(int)                                 # quem de fato pagaria (só existe na simulação)
y_hist = ((z - 0.6 * g + r.normal(0, 0.5, n)) > 0).astype(int)   # decisões históricas, enviesadas contra o grupo 1
NOMES = ["renda", "tempo_emprego", "razao_divida", "cep_score", "score_historico"]
X = np.c_[renda, emprego, divida, cep, score]
Xa, Xte, ya, yte, ga, gte, yra, yrte = train_test_split(X, y_hist, g, y_real, test_size=0.3, random_state=0, stratify=y_hist)   # teste: 30%
Xtr, Xva, ytr, yva, gtr, gva, yrtr, yrva = train_test_split(Xa, ya, ga, yra, test_size=0.25, random_state=1, stratify=ya)       # treino e validação
print("Treino: %d | validação (calibração): %d | teste: %d" % (len(ytr), len(yva), len(yte)))

print("Taxa de aprovação NOS DADOS HISTÓRICOS  : grupo 0 = %.2f | grupo 1 = %.2f" % (ytr[gtr == 0].mean(), ytr[gtr == 1].mean()))
print("Taxa de bons pagadores (verdade, só aqui): grupo 0 = %.2f | grupo 1 = %.2f" % (yrtr[gtr == 0].mean(), yrtr[gtr == 1].mean()))
```
```saída
Treino: 3150 | validação (calibração): 1050 | teste: 1800
Taxa de aprovação NOS DADOS HISTÓRICOS  : grupo 0 = 0.51 | grupo 1 = 0.29
Taxa de bons pagadores (verdade, só aqui): grupo 0 = 0.50 | grupo 1 = 0.50
```

Veja a injustiça embutida nos dados: os dois grupos têm **praticamente a mesma proporção de bons pagadores**, mas o grupo 1 foi **aprovado bem menos** no histórico. Qualquer AutoML que otimize a acurácia contra esses rótulos vai **aprender a reproduzir** essa diferença, e a fará parecer "objetiva".

Vamos treinar um modelo de boosting (LightGBM) nos rótulos históricos e explicá-lo com três ferramentas.

- **Importância por permutação:** embaralha-se uma coluna do teste e mede-se **quanto a acurácia cai**. Se cai muito, a coluna importa. É simples e vale para qualquer modelo.
- **Valores SHAP** (Lundberg; Lee, 2017): atribuem a cada atributo a sua **contribuição** para a previsão de **cada exemplo**, com base nos **valores de Shapley** da teoria dos jogos. Somando os valores absolutos médios, obtém-se uma importância global; olhando um exemplo, uma explicação local.
- **LIME** (Ribeiro; Singh; Guestrin, 2016): explica **uma decisão** ajustando um modelo simples na vizinhança dela. Não vamos rodá-lo aqui, mas é a terceira ferramenta mais citada.

:::cotidiano Analogia: dividir a conta do restaurante
Imagine que um grupo de amigos pede vários pratos e a conta chega. Como dividir **de forma justa** o que cada um deve, sabendo que alguns pratos foram compartilhados? Os valores de Shapley respondem calculando a **contribuição média de cada pessoa** em todas as ordens possíveis de chegada. O SHAP faz o mesmo com os atributos: divide a "conta" (a diferença entre a previsão e a previsão média) entre eles.
:::

```python
import lightgbm as lgb
import shap
from sklearn.inspection import permutation_importance
import os; os.makedirs("resultados", exist_ok=True)

modelo = lgb.LGBMClassifier(n_estimators=150, learning_rate=0.05, num_leaves=15, random_state=0, verbose=-1).fit(Xtr, ytr)
print("Acurácia contra os rótulos históricos: %.3f" % modelo.score(Xte, yte))

pi = permutation_importance(modelo, Xte, yte, n_repeats=10, random_state=0, scoring="accuracy")
explicador = shap.TreeExplainer(modelo); sv = explicador.shap_values(Xte); sv = sv[1] if isinstance(sv, list) else sv
base = float(np.ravel(explicador.expected_value)[-1])        # valor-base: margem média do modelo (em log-odds)
shap_global = np.abs(sv).mean(0)
print("\nImportância dos atributos (SHAP em log-odds):")
print(f"  {'atributo':<16s} {'permutação (queda de acurácia)':>32s} {'SHAP médio |valor|':>20s}")
for i in np.argsort(-shap_global): print(f"  {NOMES[i]:<16s} {pi.importances_mean[i]:>32.3f} {shap_global[i]:>20.3f}")

i = 0; p = modelo.predict_proba(Xte[i:i + 1])[0, 1]
margem = base + sv[i].sum(); p_shap = 1 / (1 + np.exp(-margem))
print(f"\nExplicação local da pessoa #{i} (grupo = {gte[i]}), contribuições em log-odds:")
for j in np.argsort(-np.abs(sv[i])): print(f"  {NOMES[j]:<16s} valor = {Xte[i, j]:7.2f}   contribuição SHAP = {sv[i, j]:+.2f}")
print(f"  valor-base = {base:+.2f} | soma das contribuições = {sv[i].sum():+.2f} | margem = {margem:+.2f}")
print(f"  probabilidade = 1 / (1 + exp(-margem)) = {p_shap:.4f} | predict_proba do modelo = {p:.4f}")
json.dump({"nomes": NOMES, "perm": pi.importances_mean.tolist(), "shap": shap_global.tolist(), "local": sv[i].tolist(), "valores": Xte[i].tolist(), "p": float(p), "base": base, "margem": float(margem)},
          open("resultados/f13_expl.json", "w"))
```
```saída

  renda                                       0.116                1.348
```

![f13_importancia](Figura 13.3 — Importância dos atributos por permutação e por SHAP, ambas normalizadas para comparação (esquerda), e explicação local de uma pessoa em log-odds (direita).)

**Em que escala estão os valores SHAP?** Este é um ponto que costuma gerar erros de leitura. Para um classificador binário de árvores (como o LightGBM), o `TreeExplainer` explica, por padrão, a **margem bruta** do modelo, isto é, o **logaritmo da razão de chances** (*log-odds*), e **não** a probabilidade. A explicação local obedece a uma conta de soma:

$$ margem = valor-base + Σ contribuições SHAP,   P(aprovar) = 1 / (1 + e^(−margem)) $$

O **valor-base** é a margem média do modelo. Cada contribuição empurra a margem para cima (positiva) ou para baixo (negativa), em **log-odds**: uma contribuição de −1,7 **não** significa "menos 1,7 ponto percentual de probabilidade". A saída mostra a conferência numérica: o valor-base mais a soma das contribuições, passado pela função logística, reproduz exatamente o `predict_proba` do modelo. Para comunicar a uma pessoa leiga, converta: compare a probabilidade com e sem o atributo, ou use a margem apenas como ordenação de importância.

Duas ferramentas diferentes, mesma história: a **renda** domina. Isso é plausível, mas esconde um fato: a renda do grupo 1 é menor por razões estruturais, e, portanto, **usar a renda é, em parte, usar o grupo**. A explicação mostra *o que* o modelo usa; ela **não** diz se o uso é **justo**. Para isso precisamos de outras medidas.

:::atencao Atenção: explicar não é justificar
Uma explicação mostra **como** o modelo chegou à decisão, não se a decisão é **correta ou justa**. Um modelo enviesado pode ser perfeitamente explicável.
:::

## 13.3 Justiça e vieses

### 13.3.1 De onde vem o viés?

O viés raramente nasce do algoritmo; ele costuma **entrar pelos dados** (Mehrabi *et al.*, 2021). Algumas fontes:

- **Viés histórico:** os dados refletem decisões humanas injustas do passado (nosso exemplo).
- **Viés de representação:** um grupo aparece pouco nos dados e o modelo aprende mal sobre ele.
- **Viés de medição:** a variável medida é um mau retrato do que importa (por exemplo, "gastos médicos" como medida de "gravidade").
- **Viés de feedback:** as decisões do modelo mudam os dados futuros e reforçam a distorção.

O AutoML **não corrige** nenhum deles; ao contrário, **otimiza** a métrica que você der, inclusive reproduzindo o viés, só que mais eficientemente.

### 13.3.2 Como medir

Duas medidas simples, ambas calculadas **por grupo** (Hardt; Price; Srebro, 2016, para a segunda):

- **Taxa de seleção:** a proporção de pessoas **aprovadas** em cada grupo. Se for muito diferente, há **disparidade**. Igualar as taxas de seleção entre os grupos é o critério da **paridade demográfica**.
- **Igualdade de oportunidade:** entre as pessoas que **de fato mereceriam** a aprovação (os verdadeiros positivos), a **taxa de aprovação** deve ser **igual** entre os grupos. É a **taxa de verdadeiros positivos (TPR)** por grupo.

:::atencao Atenção: paridade demográfica não é igualdade de oportunidade
São critérios **diferentes**. Igualar as taxas de seleção **não garante** igualar as TPR, e igualar as TPR **não garante** igualar as taxas de seleção, salvo em situações especiais (por exemplo, quando as proporções de merecedores são iguais nos grupos). Hardt, Price e Srebro (2016) propõem a igualdade de oportunidade justamente como alternativa que **depende dos rótulos** (de quem merecia) e, por isso, exige rótulos confiáveis. Escolher o critério é uma decisão de contexto, não um detalhe técnico.
:::

![f13_metricas](Figura 13.4 — Taxa de seleção e igualdade de oportunidade: duas formas de comparar grupos.)

Em dados reais, a "verdade" (quem mereceria) quase nunca é conhecida; nós a conhecemos **porque simulamos**. Isso é um privilégio didático: mostra o que acontece de fato, e nos lembra de que, no mundo real, medimos a justiça com **rótulos que podem ser eles mesmos enviesados**.

### 13.3.3 "Basta remover o atributo sensível?"

A tentação é simples: **retirar** a coluna do grupo e do CEP-score e considerar o problema resolvido. Vamos testar. Treinamos o mesmo boosting em duas versões: **com** o CEP-score (o proxy) e **sem** ele. Em nenhuma delas o modelo recebe o atributo "grupo".

```python
from sklearn.ensemble import HistGradientBoostingClassifier
res = {}
print(f"{'versão':<10s} {'acurácia':>9s} | {'seleção g0':>10s} {'seleção g1':>10s} | {'TPR real g0':>11s} {'TPR real g1':>11s}")
for nome, cols in (("com CEP", [0, 1, 2, 3, 4]), ("sem CEP", [0, 1, 2, 4])):
    m = HistGradientBoostingClassifier(random_state=0).fit(Xtr[:, cols], ytr); p = m.predict(Xte[:, cols])
    sel = [p[gte == k].mean() for k in (0, 1)]; tpr = [p[(gte == k) & (yrte == 1)].mean() for k in (0, 1)]
    res[nome] = {"sel": sel, "tpr": tpr}
    print(f"{nome:<10s} {(p == yte).mean():>9.3f} | {sel[0]:>10.3f} {sel[1]:>10.3f} | {tpr[0]:>11.3f} {tpr[1]:>11.3f}")
```
```saída
versão      acurácia | seleção g0 seleção g1 | TPR real g0 TPR real g1
com CEP        0.800 |      0.474      0.357 |       0.820       0.638
sem CEP        0.792 |      0.475      0.390 |       0.814       0.677
```

Retirar o CEP-score **não resolveu**: sem ele, o grupo 1 continua sendo aprovado bem menos (0,39 contra 0,48), e, entre os que de fato pagariam (**TPR real**), o grupo 1 é aprovado em proporção claramente menor (0,68 contra 0,81). O motivo é que outras variáveis (como a **renda**) também carregam informação sobre o grupo, e porque o modelo foi **treinado em rótulos enviesados**. Isso é o **efeito proxy**: o viés circula por variáveis correlacionadas.

![f13_proxy](Figura 13.5 — O viés não some ao apagar uma coluna: ele circula por variáveis correlacionadas e pelos próprios rótulos.)

### 13.3.4 Mitigação: ajustar o limiar por grupo, sem usar o teste

Há várias famílias de mitigação: antes do treino (rebalancear dados), durante o treino (restrições) e **depois** (ajustar a decisão). Vamos usar a mais simples: **limiares diferentes por grupo**. O modelo gera uma **probabilidade**; normalmente aprovamos quando ela passa de 0,5. Aqui, o limiar do grupo 1 será diferente. A ideia de ajustar a decisão pós-treino para atender critérios de igualdade vem de Hardt, Price e Srebro (2016).

O protocolo é o convencional, em três passos:

1. **Treinar** o modelo no conjunto de treino.
2. **Escolher os limiares na validação** (o conjunto de calibração), sem olhar o teste.
3. **Congelar** os limiares e avaliar a regra **uma única vez** no teste.

Compararemos três regras: o **limiar único** (0,5); a **paridade demográfica** (o limiar do grupo 1 é escolhido na validação para igualar a taxa de seleção do grupo 0); e a **igualdade de oportunidade com os rótulos disponíveis** (o limiar do grupo 1 é escolhido na validação para igualar a TPR calculada contra os **rótulos históricos**, os únicos que existiriam na vida real). Por fim, uma quarta linha mostra a variante **transdutiva**, em que o limiar é calculado sobre as pontuações do próprio teste (sem usar seus rótulos). Ela pode ser legítima em alguns cenários, mas **adapta a regra ao conjunto que será avaliado**; por isso precisa ser declarada como tal, e não é o protocolo recomendado.

```python
import os; os.makedirs("resultados", exist_ok=True)
modelo = lgb.LGBMClassifier(n_estimators=150, learning_rate=0.05, num_leaves=15, random_state=0, verbose=-1).fit(Xtr, ytr)
pva, pte = modelo.predict_proba(Xva)[:, 1], modelo.predict_proba(Xte)[:, 1]

# 2. limiares escolhidos SOMENTE na validação
sel0 = (pva[gva == 0] >= 0.5).mean()
t_paridade = np.quantile(pva[gva == 1], 1 - sel0)                     # iguala a taxa de seleção (paridade demográfica)
alvo = (pva[(gva == 0) & (yva == 1)] >= 0.5).mean()                   # TPR do grupo 0 contra os rótulos históricos
cand = np.linspace(0.05, 0.9, 171)
t_oport = min(cand, key=lambda t: abs((pva[(gva == 1) & (yva == 1)] >= t).mean() - alvo))   # iguala a TPR histórica
t_transd = np.quantile(pte[gte == 1], 1 - (pte[gte == 0] >= 0.5).mean())                    # variante transdutiva (usa o teste!)

# 3. regras congeladas, avaliadas uma vez no teste
def relatorio(nome, t1):
    pred = np.where(gte == 0, pte >= 0.5, pte >= t1).astype(int)
    sel = [pred[gte == k].mean() for k in (0, 1)]
    tprh = [pred[(gte == k) & (yte == 1)].mean() for k in (0, 1)]; tprr = [pred[(gte == k) & (yrte == 1)].mean() for k in (0, 1)]
    print(f"{nome:<24s} {t1:4.2f} {(pred == yte).mean():6.3f} {(pred == yrte).mean():6.3f} | {sel[0]:.2f}/{sel[1]:.2f} | {tprh[0]:.2f}/{tprh[1]:.2f} | {tprr[0]:.2f}/{tprr[1]:.2f}")
    return {"sel": sel, "tpr": tprr}

print(f"{'regra':<24s} {'t(g1)':>4s} {'acc_h':>6s} {'acc_v':>6s} | {'seleção':>9s} | {'TPR hist':>9s} | {'TPR real':>9s}")
base_r = relatorio("limiar único", 0.5)
dp_r = relatorio("paridade demográfica", t_paridade)
eo_r = relatorio("oport. (rótulos hist.)", t_oport)
relatorio("paridade (transdutiva)", t_transd)
json.dump({"base": base_r, "dp": dp_r, "eo": eo_r}, open("resultados/f13_just.json", "w"))
```
```saída
regra                    t(g1)  acc_h  acc_v |   seleção |  TPR hist |  TPR real
limiar único             0.50  0.809  0.846 | 0.49/0.38 | 0.79/0.83 | 0.84/0.67
paridade demográfica     0.29  0.785  0.857 | 0.49/0.52 | 0.79/0.92 | 0.84/0.84
oport. (rótulos hist.)   0.48  0.811  0.849 | 0.49/0.39 | 0.79/0.85 | 0.84/0.70
paridade (transdutiva)   0.33  0.793  0.857 | 0.49/0.49 | 0.79/0.91 | 0.84/0.81
```

![f13_justica](Figura 13.6 — Taxa de seleção e TPR real por grupo no teste, com limiares escolhidos na validação: limiar único, paridade demográfica e igualdade de oportunidade com rótulos históricos.)

Leia a tabela com calma (`acc_h`: acurácia contra o histórico; `acc_v`: acurácia contra a verdade da simulação; `seleção`, `TPR hist` e `TPR real`: valores dos grupos 0/1). Observe com honestidade:

- **Paridade demográfica, calibrada na validação:** o limiar do grupo 1 cai para cerca de 0,29. No teste, a taxa de seleção fica próxima nos dois grupos (0,49 e 0,52: a regra congelada **não** iguala exatamente, pois o teste é outra amostra), o **TPR real** do grupo 1 sobe de 0,67 para 0,84, e a acurácia contra a verdade sobe de 0,846 para 0,857. A acurácia contra o **histórico** (o que o AutoML otimizava) cai de 0,809 para 0,785, porque o histórico estava enviesado.
- **Igualdade de oportunidade com rótulos históricos:** o limiar quase não muda (0,48), e o TPR real do grupo 1 continua baixo (0,70). O motivo é que o critério trata como "merecedor" quem o **histórico enviesado** aprovou. Esse é o limite apontado por Hardt, Price e Srebro (2016): a igualdade de oportunidade é tão boa quanto os rótulos em que se apoia.
- **Variante transdutiva:** o resultado é parecido com o da paridade calibrada na validação (TPR real 0,81), mas o limiar foi ajustado ao **próprio teste**, o que não é um procedimento válido de avaliação quando o objetivo é estimar o desempenho da regra em dados novos.

Esse é um resultado **de simulação**: construímos a "verdade" para que a diferença fosse visível. Na vida real, a correção **não** é mágica. Há **trade-offs**: as definições de justiça podem entrar em conflito entre si (Mehrabi *et al.*, 2021), nem sempre é possível atender a todas ao mesmo tempo, e **escolher o critério é uma decisão humana e social**, não técnica.

:::atencao Atenção: o que não se deve concluir
Não conclua que "o ajuste de limiares resolve o viés". Concluiu-se apenas que, **neste cenário simulado**, a paridade demográfica calibrada na validação reduziu a disparidade e não prejudicou a acurácia contra a verdade. Em dados reais, a verdade é desconhecida, e o uso de atributos sensíveis para decisões pode ser **restrito por lei**. Consulte sempre especialistas jurídicos e das áreas afetadas.
:::

## 13.4 Calibração, incerteza e abstenção

Até aqui, olhamos para a **decisão** (aprovar ou não). Mas um modelo de AutoML devolve, na maioria das vezes, **probabilidades**, e elas também precisam de cuidado. Duas perguntas: **a probabilidade é confiável?** (calibração) e **o modelo sabe quando não sabe?** (incerteza e abstenção).

### 13.4.1 Calibração: "70%" significa 70%?

Um modelo está **calibrado** quando, entre os casos em que ele diz "70% de chance", cerca de 70% de fato acontecem. Modelos muito flexíveis, como um boosting ajustado de forma agressiva, tendem a ser **superconfiantes** (Guo *et al.*, 2017, discutem o fenômeno em redes neurais). A calibração mede-se com:

- o **escore de Brier:** o erro quadrático médio entre a probabilidade prevista e o resultado (0 ou 1); menor é melhor;
- a **perda logarítmica:** penaliza fortemente probabilidades confiantes e erradas;
- o **erro de calibração esperado** (ECE): agrupa as previsões em faixas de probabilidade e mede, em média, a distância entre a probabilidade prevista e a frequência observada em cada faixa.

A correção usual é treinar um **calibrador** (regressão logística sobre a pontuação, método "sigmoide", ou regressão isotônica) **em dados que não foram usados no treino do modelo**, aqui, a validação. Vamos comparar o modelo do capítulo, bem calibrado, com um boosting deliberadamente **agressivo** (600 árvores, taxa de aprendizado 0,1, 63 folhas), antes e depois de calibrar. O teste só mede.

```python
from sklearn.calibration import CalibratedClassifierCV
from sklearn.frozen import FrozenEstimator
from sklearn.metrics import brier_score_loss, log_loss

def ece(p, y, faixas=10):
    f = np.minimum((p * faixas).astype(int), faixas - 1); e = 0.0
    for k in range(faixas):
        m = f == k
        if m.any(): e += m.mean() * abs(p[m].mean() - y[m].mean())
    return e

agressivo = lgb.LGBMClassifier(n_estimators=600, learning_rate=0.1, num_leaves=63, random_state=0, verbose=-1).fit(Xtr, ytr)
candidatos = [("modelo do capítulo, bruto", modelo),
              ("agressivo, bruto", agressivo),
              ("agressivo + sigmoide (val.)", CalibratedClassifierCV(FrozenEstimator(agressivo), method="sigmoid").fit(Xva, yva)),
              ("agressivo + isotônica (val.)", CalibratedClassifierCV(FrozenEstimator(agressivo), method="isotonic").fit(Xva, yva))]
print(f"{'modelo':<30s} {'Brier':>7s} {'perda log':>10s} {'ECE':>7s}")
for nome, mdl in candidatos:
    p = mdl.predict_proba(Xte)[:, 1]
    print(f"{nome:<30s} {brier_score_loss(yte, p):7.4f} {log_loss(yte, p):10.4f} {ece(p, yte):7.4f}")
```
```saída
modelo                           Brier  perda log     ECE
modelo do capítulo, bruto       0.1329     0.4145  0.0285
agressivo, bruto                0.1956     1.1272  0.1803
agressivo + sigmoide (val.)     0.1508     0.4574  0.0257
agressivo + isotônica (val.)    0.1538     0.5368  0.0396
```

O boosting agressivo é **superconfiante**: ECE de 0,180 (contra 0,029 do modelo do capítulo) e perda logarítmica de 1,13 (contra 0,41). Depois de calibrado em dados separados, o ECE cai para 0,026 (sigmoide) e a perda logarítmica para 0,46, perto do modelo comportado; a regressão isotônica, com poucos dados de calibração, ficou um pouco pior que a sigmoide (ECE 0,040). Não há calibrador universalmente melhor: compare na validação. Note que a calibração melhora as **probabilidades**; a acurácia (a decisão em 0,5) quase não muda. Isso importa sempre que a probabilidade é usada para algo além do corte: priorizar casos, precificar risco, estimar custos esperados.

### 13.4.2 Predição conforme: conjuntos de previsão com garantia

Um modelo pode dizer "aprovar" com 51% de confiança ou com 99%. Como transformar essa diferença em uma garantia utilizável? A **predição conforme** (*conformal prediction*) constrói, para cada pessoa, um **conjunto de classes plausíveis** em vez de uma única classe, com uma garantia de cobertura que **não depende do modelo** nem da distribuição dos dados, desde que os casos novos sejam **trocáveis** com os da calibração, como em amostras sorteadas da mesma população (Vovk; Gammerman; Shafer, 2005; Angelopoulos; Bates, 2023).

A versão mais simples, a **conforme dividida** (*split conformal*), para duas classes, funciona assim:

1. Em um conjunto de **calibração**, calcule o **escore de não conformidade** de cada caso: **1 menos a probabilidade atribuída à classe verdadeira**. Quanto mais o modelo "se enganou" naquele caso, maior o escore.
2. Escolha o **quantil** *q* desses escores correspondente à cobertura desejada (por exemplo, 90%), com a pequena correção de amostra finita (⌈(n + 1)(1 − α)⌉ / n).
3. Para um caso novo, o conjunto de previsão contém **todas as classes cuja probabilidade é pelo menos 1 − q**.

Quando o conjunto tem **uma** classe, o modelo está seguro; quando tem **duas**, está em dúvida e o caso pode ser **encaminhado a uma pessoa** (abstenção). Usaremos a validação como calibração e o modelo bruto do capítulo (a garantia de cobertura vale para qualquer modelo, calibrado ou não; mas, se fôssemos calibrar o modelo *e* aplicar a conforme, precisaríamos de conjuntos **disjuntos** para as duas etapas).

```python
alfa = 0.10                                                          # cobertura desejada: 90%
pv, pt = modelo.predict_proba(Xva), modelo.predict_proba(Xte)
escores = 1 - pv[np.arange(len(yva)), yva]                           # não conformidade na calibração (rótulos disponíveis)
n_cal = len(escores)
q = np.quantile(escores, min(1.0, np.ceil((n_cal + 1) * (1 - alfa)) / n_cal), method="higher")
conjunto = pt >= 1 - q                                               # matriz (teste x 2 classes): classe incluída?
coberto = conjunto[np.arange(len(yte)), yte]
tamanho = conjunto.sum(1); unitario = tamanho == 1; pred = pt.argmax(1)

print(f"Cobertura desejada: {1 - alfa:.0%} | cobertura no teste: {coberto.mean():.3f}")
print(f"Cobertura por grupo: grupo 0 = {coberto[gte == 0].mean():.3f} | grupo 1 = {coberto[gte == 1].mean():.3f}")
print(f"Tamanho médio do conjunto: {tamanho.mean():.2f} | conjuntos com 2 classes (abstenção): {(tamanho == 2).mean():.1%}")
print(f"Acurácia nos casos com conjunto unitário: {(pred[unitario] == yte[unitario]).mean():.3f} | acurácia em todos os casos: {(pred == yte).mean():.3f}")
```
```saída
Cobertura desejada: 90% | cobertura no teste: 0.903
Cobertura por grupo: grupo 0 = 0.901 | grupo 1 = 0.907
Tamanho médio do conjunto: 1.22 | conjuntos com 2 classes (abstenção): 22.1%
Acurácia nos casos com conjunto unitário: 0.875 | acurácia em todos os casos: 0.809
```

Leia o resultado: a cobertura no teste fica **muito perto do alvo** de 90%, como a teoria promete (a garantia é **média**, e pequenas oscilações são esperadas por causa do tamanho finito do teste). O modelo **abstém-se** em cerca de um quinto dos casos (conjuntos com as duas classes), e, nos demais, a acurácia sobe de 0,81 para cerca de 0,88. Em outras palavras, a abstenção troca **cobertura de decisão** por **confiabilidade**: o modelo decide menos casos, mas decide melhor.

:::atencao Atenção: três cuidados com a conforme
**(1) A garantia é marginal:** vale na média da população, e **não** necessariamente em cada subgrupo. Aqui as coberturas por grupo ficaram próximas, mas isso **não é garantido**; uma versão **condicional ao grupo** (calcular um quantil por grupo na calibração) corrige o problema quando for preciso. **(2) A calibração precisa de dados separados:** se o AutoML usou a validação para **escolher** o modelo, ela não pode também servir de calibração sem perder a validade; reserve um conjunto de calibração **depois** da seleção automática. **(3) Rótulos enviesados geram garantias enviesadas:** a cobertura é medida contra os rótulos que temos, e, no nosso caso, são os históricos.
:::

### 13.4.3 Depois da seleção automática

Resumindo o protocolo para um modelo escolhido por AutoML: separe um conjunto de **calibração** que **não participou** da busca, nem do treino; calibre as probabilidades; construa os conjuntos de previsão (se a decisão for de risco); defina com as pessoas responsáveis **o que fazer com os casos em que o modelo se abstém**; e só então meça tudo no **teste**, uma única vez.

## 13.5 O custo da busca

Cada modelo avaliado consome tempo de computação e **energia**. Strubell, Ganesh e McCallum (2019) mostraram que treinar e ajustar modelos de linguagem tem custo energético e de carbono considerável, e que a **busca** multiplica esse custo. Schwartz *et al.* (2020) propõem a **IA verde**: informar o custo computacional junto com a acurácia e valorizar a eficiência.

Para estimar o custo de um AutoML, o ponto de partida é simples: **contar quantos modelos serão treinados**.

```python
estrategias = {
    "Grade 5x5x5 com validação cruzada de 5 partes": 5 * 5 * 5 * 5,
    "Aleatória: 60 sorteios, validação cruzada de 5": 60 * 5,
    "Bayesiana (TPE): 60 tentativas, validação cruzada de 5": 60 * 5,
    "Aleatória: 60 sorteios, holdout (1 divisão)": 60 * 1,
    "Halving/Hyperband: ~30 treinos completos equivalentes": 30,
    "Modelo padrão, sem busca": 1,
}
minutos = 2
print(f"{'estratégia':<58s} {'treinos':>8s} {'horas*':>8s}")
for nome, k in estrategias.items(): print(f"{nome:<58s} {k:>8d} {k * minutos / 60:>8.1f}")
print(f"\n* supondo {minutos} minutos por treino; multiplique pelo consumo do seu hardware para estimar a energia.")
```
```saída
estratégia                                                  treinos   horas*
Grade 5x5x5 com validação cruzada de 5 partes                   625     20.8
Aleatória: 60 sorteios, validação cruzada de 5                  300     10.0
Bayesiana (TPE): 60 tentativas, validação cruzada de 5          300     10.0
Aleatória: 60 sorteios, holdout (1 divisão)                      60      2.0
Halving/Hyperband: ~30 treinos completos equivalentes            30      1.0
Modelo padrão, sem busca                                          1      0.0

* supondo 2 minutos por treino; multiplique pelo consumo do seu hardware para estimar a energia.
```

Três ideias práticas para reduzir o custo, que você já conhece: **busca aleatória em vez de grade** (Capítulo 4), **parada precoce e Hyperband** (Capítulo 6) e **warm start** (Capítulo 9). E uma ideia nova: **pergunte se a busca vale a pena**. Se um modelo padrão chega perto, gastar 100 vezes mais computação por um ganho dentro do ruído é um mau negócio.

## 13.6 Os limites do AutoML

O AutoML é poderoso, mas **não é mágico**. Seus limites merecem ficar à vista.

![f13_limites](Figura 13.7 — O que o AutoML faz bem e o que continua sendo responsabilidade humana.)

1. **Não define o problema.** Escolher o que prever, a métrica e o que é "bom" é humano.
2. **Não corrige dados ruins.** "Lixo entra, lixo sai": rótulos enviesados, vazamento e amostras não representativas passam direto (Kapoor; Narayanan, 2023).
3. **Não existe almoço grátis.** Nenhum algoritmo é o melhor em todos os problemas (Wolpert, 1996); por isso o AutoML precisa **procurar**, e por isso seus ganhos dependem do problema.
4. **Otimiza a validação, não o mundo.** Quanto mais se busca, maior o **otimismo da seleção** (Cawley; Talbot, 2010; Varma; Simon, 2006), tema dos Capítulos 2 e 4.
5. **Não prevê mudanças do mundo.** Se os dados mudam depois da implantação (deriva), o modelo envelhece (Capítulo 14).
6. **Tem custo.** Computação, energia e tempo de quem revisa os resultados.
7. **Pode esconder decisões.** Um pipeline escolhido automaticamente é mais difícil de auditar, a menos que você inspecione o resultado (Capítulo 10).

## 13.7 Lista de verificação ética para um projeto de AutoML

![f13_checklist](Figura 13.8 — Uma lista de verificação para antes, durante e depois do AutoML.)

**Antes:**
- O problema está bem definido, e a decisão que o modelo apoia afeta pessoas? Quais?
- De onde vêm os dados? Quem está **sub-representado** ou **ausente**?
- Os rótulos refletem a **verdade** ou **decisões humanas passadas**?

**Durante:**
- Há linha de base simples e modelo interpretável no espaço de busca?
- A validação respeita a estrutura dos dados (tempo, grupos, repetição de indivíduos)?
- Medi o desempenho **por grupo** e não só a média geral?

**Depois:**
- Existe **explicação** adequada ao público (técnica para quem desenvolve, simples para quem é afetado)?
- Há **canal de contestação** para quem discordar de uma decisão?
- Há **monitoramento** de desempenho, de deriva e de disparidades?
- O custo computacional foi **registrado e justificado**?

## 13.8 Boas práticas

1. **Prefira modelos interpretáveis** quando o desempenho for equivalente, sobretudo em decisões de alto risco (Rudin, 2019).
2. **Explique em dois níveis:** global (o que o modelo valoriza) e local (por que decidiu isso).
3. **Meça por grupo:** taxa de seleção e igualdade de oportunidade, e desconfie de médias gerais.
4. **Não conte com a remoção de atributos sensíveis:** procure proxies e examine os rótulos.
5. **Questione os rótulos:** modelos aprendem as decisões do passado, inclusive as injustas.
6. **Documente o custo** e evite buscas que não se justificam.
7. **Mantenha pessoas no circuito** nas decisões que afetam vidas.
8. **Seja transparente sobre limites:** relate o que o modelo **não** sabe fazer.

- **Três perguntas:** eu entendo? é justo? quanto custa e o que não faz?
- **Interpretável × pós-hoc:** em alto risco, prefira o interpretável; no empate técnico, o simples (Rudin, 2019).
- **Global × local:** o que o modelo valoriza × por que decidiu isto.
