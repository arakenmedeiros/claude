## 9.5 Anatomia de uma aplicação com LLM

Uma aplicação com LLM costuma ter cinco etapas em sequência:

1. **Preparar a entrada**: limpar, mascarar dados pessoais, montar o prompt, contar tokens.
2. **Chamar o modelo**: via serviço remoto ou modelo local, com tempo limite e novas tentativas.
3. **Validar a saída**: formato, esquema, regras de negócio, verificações (Capítulo 8).
4. **Tratar falhas**: nova tentativa, plano B, encaminhamento a humano.
5. **Registrar**: versão do prompt, modelo, parâmetros, métricas e resultado.

![f09_camadas]([C] As camadas de uma aplicação com LLM. A lógica da aplicação depende de uma interface, e não de um provedor específico; os adaptadores traduzem a interface para cada serviço ou modelo local.)

### 9.5.1 Separar a lógica do provedor

O erro mais caro é deixar a lógica de negócio **acoplada** a um provedor: espalhar chamadas específicas por todo o código. A solução clássica é o padrão de **portas e adaptadores**: a aplicação depende de uma **interface** abstrata (a "porta"), e cada provedor é implementado em um **adaptador**.

Em Python, `typing.Protocol` descreve a interface sem herança obrigatória. Veja a nossa:

```python
from dataclasses import dataclass, field
from typing import Protocol

@dataclass
class Mensagem:
    papel: str          # "system", "user" ou "assistant"
    conteudo: str

@dataclass
class Parametros:
    temperatura: float = 0.0
    max_tokens: int = 300
    tempo_limite_s: float = 30.0

@dataclass
class Resposta:
    texto: str
    tokens_entrada: int = 0
    tokens_saida: int = 0
    modelo: str = ""
    extra: dict = field(default_factory=dict)

class ProvedorLLM(Protocol):
    nome: str
    def gerar(self, mensagens: list[Mensagem], params: Parametros) -> Resposta: ...
```

Um **provedor simulado** permite desenvolver e testar tudo sem acesso a serviços. Este responde extraindo a frase mais parecida com a pergunta do contexto fornecido (como o "modelo de brinquedo" do Capítulo 1). **Ele não é um LLM.**

```python+
import re
from llmdidatico import DOCS, modelos

class ProvedorSimulado:
    nome = "simulado"
    def gerar(self, mensagens, params):
        usuario = next(m.conteudo for m in reversed(mensagens) if m.papel == "user")
        ctx, _, pergunta = usuario.partition("\nPERGUNTA: ")
        frases = [f.strip() for f in re.split(r"(?<=[.!?])\s+", ctx.replace("CONTEXTO:", "")) if f.strip()]
        if not frases:
            texto = "não consta"
        else:
            q = set(modelos.tokenizar_sem_stop(pergunta))
            pontos = [len(q & set(modelos.tokenizar_sem_stop(f))) for f in frases]
            texto = frases[pontos.index(max(pontos))] if max(pontos) > 0 else "não consta"
        return Resposta(texto=texto, tokens_entrada=len(usuario.split()), tokens_saida=len(texto.split()), modelo="simulado-v1")

class Assistente:
    """Lógica da aplicação: recupera contexto, monta o prompt, chama o provedor e valida a saída."""
    def __init__(self, provedor: ProvedorLLM):
        self.provedor = provedor
        self.bm25 = modelos.BM25([modelos.tokenizar_sem_stop(d[3]) for d in DOCS])

    def responder(self, pergunta):
        s = self.bm25.pontuar(modelos.tokenizar_sem_stop(pergunta))
        melhor = int(s.argmax())
        contexto = DOCS[melhor][3] if s[melhor] > 0 else ""
        msgs = [Mensagem("system", "Responda usando apenas o contexto. Se não houver resposta, diga: não consta."),
                Mensagem("user", f"CONTEXTO: {contexto}\nPERGUNTA: {pergunta}")]
        r = self.provedor.gerar(msgs, Parametros(temperatura=0.0, max_tokens=200))
        return {"resposta": r.texto, "fonte": DOCS[melhor][0] if contexto else None, "modelo": r.modelo}

app = Assistente(ProvedorSimulado())
for p in ["Qual o valor da multa por atraso na devolução de livros?", "Até quando posso trancar a matrícula?", "Qual a capital da Austrália?"]:
    print(app.responder(p))
```

Observe que a pergunta sem resposta na base ("capital da Austrália") recebe "não consta": a **aplicação** impôs o contexto vazio e o provedor respeitou. A lógica de negócio (recuperação, montagem de prompt, política de abstenção) está na classe `Assistente`, e não no provedor.

## 9.6 Comunicação com APIs

### 9.6.1 O que acontece em uma chamada

Um serviço de LLM em geral expõe um **endpoint HTTP**. A aplicação envia uma requisição com: (1) **autenticação** (uma chave ou token em cabeçalho); (2) o **modelo** desejado; (3) a lista de **mensagens** com papéis (sistema, usuário, assistente); (4) **parâmetros** (temperatura, limite de tokens, etc.). A resposta traz o texto gerado, a razão da parada (fim natural, limite de tokens, recusa...) e as **contagens de tokens** usadas. Muitos serviços oferecem também **streaming** (envio do texto em pedaços, útil para latência percebida).

Convenções variam entre provedores (nomes de campos, formato de mensagens, parâmetros aceitos). Por isso, usamos um **adaptador** por provedor, e sempre a **documentação oficial** como fonte.

### 9.6.2 Adaptador para o SDK da Anthropic

O código a seguir usa o SDK oficial de Python da Anthropic (`pip install anthropic`). Os nomes `Anthropic`, `messages.create`, `RateLimitError`, `APIStatusError`, `APIConnectionError` e `APITimeoutError` foram verificados como existentes na versão instalada (1.15.0), mas **a chamada de rede não foi executada**. O modelo vem de uma **variável de ambiente**, para não fixar nomes de modelos que mudam com o tempo; a credencial é lida pelo próprio SDK do ambiente (`ANTHROPIC_API_KEY`), e **nunca escrita no código**.

```python-ni
import os
import anthropic

class ProvedorAnthropic:
    nome = "anthropic"
    def __init__(self):
        self.modelo = os.environ["LLM_MODELO"]          # nome do modelo, definido fora do código
        self.cliente = anthropic.Anthropic()            # lê as credenciais do ambiente

    def gerar(self, mensagens, params):
        sistema = " ".join(m.conteudo for m in mensagens if m.papel == "system")
        conversa = [{"role": m.papel, "content": m.conteudo} for m in mensagens if m.papel != "system"]
        r = self.cliente.with_options(timeout=params.tempo_limite_s).messages.create(
            model=self.modelo, max_tokens=params.max_tokens, system=sistema, messages=conversa)
        texto = "".join(b.text for b in r.content if b.type == "text")
        return Resposta(texto=texto, tokens_entrada=r.usage.input_tokens, tokens_saida=r.usage.output_tokens, modelo=self.modelo)
```

Pontos a conferir na documentação vigente: quais parâmetros o modelo escolhido aceita (alguns modelos recentes **não aceitam** certos parâmetros de amostragem, como temperatura), limites de tokens de saída e política de uso. Por isso, o adaptador acima **não** repassa `temperatura`: parâmetros devem ser repassados apenas quando o modelo e o provedor os aceitam.

### 9.6.3 Adaptador para um serviço HTTP com interface compatível

Vários serviços e servidores locais adotam uma convenção de "conclusões de conversa" (*chat completions*), com um caminho `/chat/completions`, mensagens com `role` e `content` e a resposta em `choices[0].message.content`. O adaptador abaixo usa só a biblioteca padrão. **Verifique sempre a documentação do serviço**: caminhos, campos e parâmetros variam.

```python-ni
import json
import os
import urllib.request

class ProvedorHTTPCompativel:
    nome = "http-compativel"
    def __init__(self, base_url, modelo, nome_var_chave="LLM_CHAVE"):
        self.base_url, self.modelo = base_url.rstrip("/"), modelo
        self.chave = os.environ.get(nome_var_chave)

    def gerar(self, mensagens, params):
        corpo = {"model": self.modelo, "max_tokens": params.max_tokens, "temperature": params.temperatura,
                 "messages": [{"role": m.papel, "content": m.conteudo} for m in mensagens]}
        cab = {"Content-Type": "application/json"}
        if self.chave:
            cab["Authorization"] = f"Bearer {self.chave}"
        req = urllib.request.Request(f"{self.base_url}/chat/completions", data=json.dumps(corpo).encode("utf-8"), headers=cab)
        with urllib.request.urlopen(req, timeout=params.tempo_limite_s) as resp:
            dados = json.load(resp)
        uso = dados.get("usage", {})
        return Resposta(texto=dados["choices"][0]["message"]["content"], tokens_entrada=uso.get("prompt_tokens", 0),
                        tokens_saida=uso.get("completion_tokens", 0), modelo=self.modelo)
```

### 9.6.4 Erros, limites e novas tentativas

Os erros de uma chamada se dividem em duas famílias com tratamentos opostos:

| Tipo | Exemplos | Tratamento |
|---|---|---|
| **Transitórios** (podem passar) | Tempo esgotado; falha de rede; indisponibilidade do servidor (códigos 5xx); limite de taxa (429) | **Tentar de novo** com recuo exponencial, respeitando o tempo de espera que o serviço indicar |
| **Permanentes** (não passam) | Requisição inválida (400); credencial inválida (401); sem permissão (403); modelo inexistente (404) | **Não repetir**: corrigir a causa, registrar e alertar |

Tentar de novo erros permanentes só gasta tempo e dinheiro; não tentar de novo erros transitórios deixa o sistema frágil.

O **recuo exponencial com jitter** espaça as tentativas: após a $k$-ésima falha, espera-se

$$ t_k=\min\big(t_{\max},\ t_0\cdot2^{k}\big)\cdot(1+u),\qquad u\sim\mathrm{U}(0,\,j) $$

em que $t_0$ é o atraso inicial, $t_{\max}$ o teto e $j$ o fator de *jitter* (aleatoriedade que evita que muitos clientes tentem exatamente ao mesmo tempo). Com $t_0=1$ s e sem *jitter*, as esperas são 1, 2, 4, 8, 16 s... até o teto.

```python+
import random

class ErroTransitorio(Exception):
    """Falha que pode passar (rede, 429, 5xx, tempo esgotado)."""

class ErroPermanente(Exception):
    """Falha que não passa (400, 401, 403, 404)."""

def com_recuo(funcao, max_tentativas=5, t0=1.0, teto=30.0, jitter=0.25, dormir=lambda s: None, rng=None):
    """Chama funcao() repetindo só em ErroTransitorio. 'dormir' é injetável para testar sem esperar."""
    rng = rng or random.Random(0)
    esperas = []
    for k in range(max_tentativas):
        try:
            return funcao(), k + 1, esperas
        except ErroPermanente:
            raise
        except ErroTransitorio:
            if k == max_tentativas - 1:
                raise
            espera = min(teto, t0 * 2 ** k) * (1 + rng.uniform(0, jitter))
            esperas.append(round(espera, 2)); dormir(espera)

class ServicoInstavel:
    def __init__(self, falhas):
        self.falhas = falhas
    def __call__(self):
        if self.falhas > 0:
            self.falhas -= 1
            raise ErroTransitorio("429 limite de taxa")
        return "ok"

resultado, tentativas, esperas = com_recuo(ServicoInstavel(falhas=3))
print("resultado:", resultado, "| tentativas:", tentativas, "| esperas (s):", esperas)

try:
    com_recuo(ServicoInstavel(falhas=10), max_tentativas=4)
except ErroTransitorio as e:
    print("esgotou as tentativas:", e)

def servico_com_chave_invalida():
    raise ErroPermanente("401 credencial inválida")
try:
    com_recuo(servico_com_chave_invalida)
except ErroPermanente as e:
    print("erro permanente, sem repetição:", e)
```

O primeiro caso mostra esperas crescentes (aproximadamente 1, 2 e 4 segundos, com o *jitter*); o segundo mostra que, esgotado o limite, o erro é propagado; o terceiro, que um erro permanente **não** é repetido. Em produção, `dormir` seria `time.sleep`. Note que `dormir` é **injetável**: isso permite testar o comportamento sem esperar, uma técnica valiosa.

:::pratica Na prática: o que os SDKs oficiais já fazem
Os SDKs oficiais de muitos provedores já implementam novas tentativas automáticas para erros transitórios, com recuo, e permitem configurar o número de tentativas e o tempo limite. Antes de escrever o seu laço, leia a documentação do SDK, para não **empilhar** duas camadas de novas tentativas (o que multiplica o tempo e a carga). Escreva o seu quando usar HTTP direto, quando houver política de aplicação (por exemplo, trocar de provedor após a falha) ou para testar.
:::

## 9.7 Execução de modelos locais

Executar o modelo na própria máquina ou servidor tem vantagens (dados não saem do ambiente, custo previsível, independência de serviços) e custos (hardware, manutenção, qualidade geralmente menor que a dos maiores modelos comerciais). Há três caminhos comuns:

| Caminho | O que é | Observação |
|---|---|---|
| **Biblioteca Transformers** | Carrega pesos e executa o modelo em Python (geralmente com PyTorch) | Muito flexível; exige memória de GPU ou paciência em CPU |
| **Motores otimizados para CPU/GPU modestas** | Executam modelos quantizados em formatos próprios (por exemplo, o ecossistema do *llama.cpp*) | Menor memória; menor qualidade que a precisão total |
| **Servidores locais** | Programas que expõem o modelo por uma API HTTP local | Permitem usar o **mesmo adaptador HTTP** do serviço remoto |

### 9.7.1 Exemplo com a biblioteca Transformers

O trecho a seguir segue o padrão da documentação da biblioteca: carregar o tokenizador e o modelo, aplicar o **modelo de conversa** (Capítulo 7), gerar e decodificar **apenas os tokens novos**. Os nomes `AutoTokenizer`, `AutoModelForCausalLM` e `apply_chat_template` foram verificados como existentes na versão instalada (5.20.1). **Nada foi executado**, pois não havia modelos nem PyTorch neste ambiente; `NOME_DO_MODELO` é um marcador: escolha um modelo cuja **licença** permita o seu uso.

```python-ni
from transformers import AutoTokenizer, AutoModelForCausalLM

NOME_DO_MODELO = "ORGANIZACAO/NOME-DO-MODELO"      # marcador: verifique a licença e o tamanho antes de baixar
tok = AutoTokenizer.from_pretrained(NOME_DO_MODELO)
modelo = AutoModelForCausalLM.from_pretrained(NOME_DO_MODELO)

class ProvedorLocal:
    nome = "local-transformers"
    def gerar(self, mensagens, params):
        conversa = [{"role": m.papel, "content": m.conteudo} for m in mensagens]
        entrada = tok.apply_chat_template(conversa, add_generation_prompt=True, return_tensors="pt", return_dict=True)
        saida = modelo.generate(**entrada, max_new_tokens=params.max_tokens, do_sample=False)
        novos = saida[0][entrada["input_ids"].shape[-1]:]       # só os tokens gerados
        texto = tok.decode(novos, skip_special_tokens=True)
        return Resposta(texto=texto, tokens_entrada=int(entrada["input_ids"].shape[-1]), tokens_saida=len(novos), modelo=NOME_DO_MODELO)
```

Cuidado: a biblioteca evolui rápido; nomes de parâmetros de carregamento (por exemplo, o tipo numérico dos pesos e o posicionamento em dispositivos) mudam entre versões principais. Consulte a documentação da versão instalada.

### 9.7.2 Pesos disponíveis não são o mesmo que modelo aberto

Termos usados de forma vaga merecem precisão:

- **Modelo com pesos disponíveis** (*open-weights*): os parâmetros podem ser baixados e executados localmente. Isso **não** diz nada, por si só, sobre o que se pode fazer com eles.
- **Licença**: define usos permitidos. Algumas licenças são permissivas (uso comercial livre); outras impõem restrições (por exemplo, limites de escala, proibição de certos usos, obrigações de atribuição ou de aceitar políticas de uso). **Leia a licença do modelo específico e da versão.**
- **Modelo efetivamente aberto**: em um sentido mais forte, além dos pesos, haveria acesso a **código de treinamento, descrição dos dados e licença que permita estudar, modificar e redistribuir**. Poucos modelos grandes satisfazem tudo isso; a maioria divulga pesos, e não os dados de treinamento.

Famílias como as descritas por Touvron et al. (2023) e Jiang et al. (2023) disponibilizaram pesos, cada uma sob suas condições, que **mudam entre versões**: confira sempre o texto da licença vigente na página do modelo antes de usar comercialmente.

### 9.7.3 Cabe na minha máquina?

A memória mínima dos pesos é $N\times b$ (Capítulo 2), e é preciso somar o **cache KV** (Capítulo 6) e uma margem para ativações. O código abaixo automatiza a estimativa. Os modelos são **hipotéticos**.

```python+
def memoria_pesos_gb(n_params, bits):
    return n_params * bits / 8 / 1e9

def memoria_kv_gb(camadas, T, n_kv, d_cab, bytes_num=2):
    return 2 * camadas * T * n_kv * d_cab * bytes_num / 1e9

def cabe(n_params, bits, camadas, T, n_kv, d_cab, gb_disponiveis, margem=0.15):
    total = memoria_pesos_gb(n_params, bits) + memoria_kv_gb(camadas, T, n_kv, d_cab)
    return total, total <= gb_disponiveis * (1 - margem)

for nome, N, bits in [("7 bi, 16 bits", 7e9, 16), ("7 bi, 8 bits", 7e9, 8), ("7 bi, 4 bits", 7e9, 4), ("13 bi, 4 bits", 13e9, 4)]:
    total, ok = cabe(N, bits, camadas=32, T=4096, n_kv=8, d_cab=128, gb_disponiveis=16)
    print(f"{nome:<15} pesos+cache ≈ {total:5.1f} GB | cabe em 16 GB com 15% de margem? {ok}")
```

Quantização reduz a memória, mas pode reduzir a qualidade de modo desigual entre tarefas; **meça** (Capítulos 15 e 16). Um servidor local, como os que expõem uma API compatível, permite reaproveitar o `ProvedorHTTPCompativel` para modelos locais: troca-se apenas a URL base.

```python-ni
# Exemplo de uso do adaptador HTTP com um servidor local (a porta e o caminho dependem do servidor escolhido)
provedor_local = ProvedorHTTPCompativel(base_url="http://localhost:PORTA/v1", modelo="NOME-DO-MODELO-LOCAL")
```

## 9.8 Preparação das entradas

Antes de chamar o modelo, a aplicação deve **preparar** a entrada. Quatro tarefas frequentes:

1. **Limpeza e normalização** (Unicode, espaços, caracteres de controle).
2. **Mascaramento de dados pessoais**, para não enviar a terceiros mais do que o necessário (**minimização de dados**, LGPD; Capítulo 17).
3. **Limite de tamanho**: contar tokens **com o tokenizador do modelo** (Capítulo 3) e aplicar uma política explícita de truncamento (por exemplo, descartar o histórico mais antigo; nunca cortar silenciosamente instruções).
4. **Montagem** do prompt a partir de componentes versionados (Capítulo 8).

O mascaramento abaixo cobre padrões simples (e-mail, CPF, telefone). **Padrões reais exigem mais cuidado**: nomes, endereços e identificadores livres em texto não são detectados por expressões regulares simples, e nenhuma técnica garante a remoção completa de dados pessoais.

```python+
import re

PADROES = [
    ("EMAIL", re.compile(r"[\w.+-]+@[\w-]+\.[\w.-]+")),
    ("CPF", re.compile(r"\b\d{3}\.\d{3}\.\d{3}-\d{2}\b")),
    ("TELEFONE", re.compile(r"\(?\b\d{2}\)?\s?9?\d{4}-\d{4}\b")),
]

def mascarar(texto):
    achados = {}
    for nome, rx in PADROES:
        def troca(m, nome=nome):
            achados[nome] = achados.get(nome, 0) + 1
            return f"[{nome}]"
        texto = rx.sub(troca, texto)
    return texto, achados

entrada = "Sou Maria, CPF 123.456.789-09, e-mail maria.silva@exemplo.com.br, telefone (61) 98888-7777. Quero cancelar meu plano."
limpo, achados = mascarar(entrada)
print(limpo)
print("itens mascarados:", achados)

def aparar_historico(mensagens, tokens_por_mensagem, limite):
    escolhidas, usados = [], 0
    for m, n in zip(reversed(mensagens), reversed(tokens_por_mensagem)):
        if usados + n > limite:
            break
        escolhidas.append(m); usados += n
    return list(reversed(escolhidas)), usados

hist, usados = aparar_historico(["m1", "m2", "m3", "m4"], [300, 200, 400, 150], 800)
print("histórico mantido:", hist, "| tokens:", usados)
```

Note que o nome ("Maria") **não** foi mascarado: expressões regulares simples não detectam nomes. Quando a privacidade é requisito forte, combine técnicas (reconhecimento de entidades, listas, revisão) e avalie a taxa de falhas.

## 9.9 Validação das saídas

A validação (Capítulo 8) é o último filtro antes de a saída produzir efeitos. Em aplicações, convém validar em **três níveis**: **formato** (JSON e esquema), **conteúdo** (regras de negócio, citações, faixas plausíveis) e **política** (por exemplo, a resposta não pode conter dados pessoais ou instruções proibidas). A biblioteca `pydantic` expressa o esquema; regras adicionais são funções simples.

```python+
from typing import Optional
from pydantic import BaseModel, Field, ValidationError, field_validator

class RespostaAtendimento(BaseModel):
    resposta: str = Field(min_length=1, max_length=500)
    fonte: Optional[str] = None

    @field_validator("resposta")
    @classmethod
    def sem_dados_pessoais(cls, v):
        _, achados = mascarar(v)
        if achados:
            raise ValueError(f"a resposta contém dados pessoais: {achados}")
        return v

def validar_resposta(dicionario):
    try:
        return RespostaAtendimento(**dicionario), None
    except ValidationError as e:
        return None, e.errors()[0]["msg"]

for d in [{"resposta": "A multa é de R$ 1,50 por dia.", "fonte": "D12"},
          {"resposta": "", "fonte": "D12"},
          {"resposta": "Ligue para (61) 98888-7777 para saber mais.", "fonte": None}]:
    obj, erro = validar_resposta(d)
    print("OK    " if obj else "FALHA ", "|", d["resposta"][:42].ljust(42), "|", erro or "válida")
```

## 9.10 Orçamentos, limites e falhas na prática

Além do recuo, aplicações em produção usam proteções adicionais:

- **Orçamento por requisição e por período**: limite de tokens e de custo, que interrompe a execução quando excedido (evita fatura inesperada por laços ou ataques).
- **Limite de concorrência**: número máximo de chamadas simultâneas, para respeitar limites de taxa.
- **Disjuntor** (*circuit breaker*): depois de várias falhas seguidas, para de chamar o serviço por um tempo, devolvendo rapidamente o plano B, e testa a recuperação depois.
- **Plano B**: modelo menor, resposta em cache, regra simples ou encaminhamento a humano.
- **Tempo limite global**: a soma de tentativas não pode ultrapassar o tempo que o usuário tolera.

```python+
class Orcamento:
    def __init__(self, max_tokens_total, preco_por_mil_tokens=None):
        self.max, self.usado, self.preco = max_tokens_total, 0, preco_por_mil_tokens
    def registrar(self, tokens):
        self.usado += tokens
        if self.usado > self.max:
            raise RuntimeError(f"orçamento excedido: {self.usado} > {self.max} tokens")
    def custo(self):
        return None if self.preco is None else self.usado / 1000 * self.preco

class Disjuntor:
    def __init__(self, limite_falhas=3):
        self.limite, self.falhas, self.aberto = limite_falhas, 0, False
    def chamar(self, funcao, plano_b):
        if self.aberto:
            return plano_b(), "plano_b (disjuntor aberto)"
        try:
            r = funcao(); self.falhas = 0; return r, "principal"
        except ErroTransitorio:
            self.falhas += 1
            if self.falhas >= self.limite:
                self.aberto = True
            return plano_b(), "plano_b (falha)"

orc = Orcamento(max_tokens_total=500, preco_por_mil_tokens=2.0)       # preço hipotético
for n in (200, 200):
    orc.registrar(n)
print("tokens usados:", orc.usado, "| custo hipotético:", orc.custo())
try:
    orc.registrar(200)
except RuntimeError as e:
    print("bloqueado:", e)

d = Disjuntor(limite_falhas=2)
def sempre_falha(): raise ErroTransitorio("indisponível")
print([d.chamar(sempre_falha, lambda: "resposta padrão")[1] for _ in range(4)])
```

## 9.11 Gestão segura de credenciais

Uma chave de acesso é como uma senha **com cartão de crédito anexado**: quem a tiver usa o serviço em seu nome. Regras básicas:

1. **Nunca escreva credenciais no código** nem em arquivos versionados (Git). Um repositório é lido por muita gente e, uma vez publicado, o histórico guarda a chave para sempre.
2. **Use variáveis de ambiente ou um gerenciador de segredos.** Arquivos `.env` locais devem estar no `.gitignore`.
3. **Menor privilégio**: chaves distintas por aplicação e ambiente, com permissões e orçamentos limitados.
4. **Não registre credenciais** em logs, mensagens de erro ou telas; ao exibir, **mascare**.
5. **Rotação e revogação**: troque chaves periodicamente e imediatamente após suspeita de vazamento.
6. **Varredura automática**: ferramentas que procuram padrões de chave em commits (como etapa de CI).
7. **Falhe com clareza**: se a credencial faltar, a aplicação deve informar **qual variável** falta, sem imprimir valores.

```python+
import os

def obter_credencial(nome_variavel):
    valor = os.environ.get(nome_variavel)
    if not valor:
        raise RuntimeError(f"variável de ambiente ausente: {nome_variavel} (defina-a fora do código; nunca versione)")
    return valor

def mascarar_chave(chave):
    return "****" if len(chave) <= 8 else chave[:3] + "…" + chave[-2:]

PADROES_SEGREDO = [re.compile(r"(?i)(chave|api[_-]?key|token|senha|secret)\s*[:=]\s*['\"]?[A-Za-z0-9_\-]{12,}")]

def procurar_segredos(texto):
    return [m.group(0)[:30] + "…" for rx in PADROES_SEGREDO for m in rx.finditer(texto)]

os.environ["CHAVE_DEMO_FALSA"] = "valor-falso-abcdef123456"      # valor FALSO, só para demonstração
print("chave mascarada para exibição:", mascarar_chave(obter_credencial("CHAVE_DEMO_FALSA")))
try:
    obter_credencial("VARIAVEL_QUE_NAO_EXISTE")
except RuntimeError as e:
    print("erro claro:", e)

codigo_ruim = 'cliente = Servico(api_key="abcdef1234567890XYZ")\nprint("olá")'
print("segredos encontrados no código:", procurar_segredos(codigo_ruim))
print("segredos encontrados no código bom:", procurar_segredos('cliente = Servico(api_key=os.environ["CHAVE"])'))
```

Se uma chave vazar (por exemplo, for publicada em um repositório): **revogue-a imediatamente** no provedor, gere outra, verifique o uso suspeito e só então limpe o histórico; apagar o commit **não** desfaz o vazamento.

## 9.12 Registro de versões e parâmetros

Cada chamada deve deixar um **rastro**, para responder depois: "qual prompt, qual modelo, quais parâmetros, quanto custou, quanto demorou, deu certo?". Um registro estruturado (uma linha JSON por chamada) é simples e poderoso. Cuidado com privacidade: registre **identificadores e hashes** do conteúdo, e o texto integral apenas quando houver necessidade e base legal, com acesso controlado e retenção limitada.

```python+
import hashlib, json, tempfile, time, os, statistics
from dataclasses import asdict

def registrar_chamada(arquivo, provedor, prompt_id, params, resposta, latencia_s, status, entrada_texto):
    linha = {
        "ts": time.strftime("%Y-%m-%dT%H:%M:%S"),
        "provedor": provedor, "modelo": resposta.modelo if resposta else None,
        "prompt_id": prompt_id, "params": asdict(params),
        "tokens_entrada": resposta.tokens_entrada if resposta else 0, "tokens_saida": resposta.tokens_saida if resposta else 0,
        "latencia_s": round(latencia_s, 4), "status": status,
        "hash_entrada": hashlib.sha256(entrada_texto.encode("utf-8")).hexdigest()[:16],
    }
    with open(arquivo, "a", encoding="utf-8") as f:
        f.write(json.dumps(linha, ensure_ascii=False) + "\n")

class AssistenteRegistrado(Assistente):
    def __init__(self, provedor, arquivo_log):
        super().__init__(provedor); self.log = arquivo_log
    def responder(self, pergunta):
        t0 = time.perf_counter()
        r = super().responder(pergunta)
        resp = Resposta(texto=r["resposta"], tokens_entrada=len(pergunta.split()), tokens_saida=len(r["resposta"].split()), modelo=r["modelo"])
        registrar_chamada(self.log, self.provedor.nome, "prompt-v1", Parametros(), resp, time.perf_counter() - t0, "ok", pergunta)
        return r

with tempfile.TemporaryDirectory() as d:
    log = os.path.join(d, "chamadas.jsonl")
    app2 = AssistenteRegistrado(ProvedorSimulado(), log)
    from llmdidatico import CONSULTAS
    for q, rel, a, t in CONSULTAS[:20]:
        app2.responder(q)
    linhas = [json.loads(l) for l in open(log, encoding="utf-8")]
print("chamadas registradas:", len(linhas))
print("exemplo de registro:", {k: linhas[0][k] for k in ("provedor", "modelo", "prompt_id", "status", "tokens_entrada", "hash_entrada")})
print("latência mediana (s):", statistics.median(l["latencia_s"] for l in linhas), "| tokens de saída (soma):", sum(l["tokens_saida"] for l in linhas))
```

## 9.13 Separar a lógica da aplicação do provedor

A recompensa da arquitetura em camadas é poder **trocar o provedor sem tocar na lógica**, e **testar a lógica sem acessar serviços**. Para demonstrar, criamos um segundo provedor simulado, com comportamento diferente (por exemplo, sempre responde com a primeira frase do contexto), e verificamos que `Assistente` funciona com ambos. Também escrevemos **testes automatizados** que não usam rede.

```python+
class ProvedorPrimeiraFrase:
    nome = "primeira-frase"
    def gerar(self, mensagens, params):
        usuario = next(m.conteudo for m in reversed(mensagens) if m.papel == "user")
        ctx = usuario.partition("\nPERGUNTA: ")[0].replace("CONTEXTO:", "").strip()
        texto = re.split(r"(?<=[.!?])\s+", ctx)[0] if ctx else "não consta"
        return Resposta(texto=texto, tokens_entrada=len(usuario.split()), tokens_saida=len(texto.split()), modelo="primeira-frase-v1")

def teste_abstencao(provedor):
    r = Assistente(provedor).responder("Qual a capital da Austrália?")
    assert r["resposta"] == "não consta" and r["fonte"] is None

def teste_cita_fonte(provedor):
    r = Assistente(provedor).responder("Qual o valor da multa por atraso na devolução de livros?")
    assert r["fonte"] == "D12" and "R$ 1,50" in r["resposta"]

for prov in (ProvedorSimulado(), ProvedorPrimeiraFrase()):
    resultados = []
    for teste in (teste_abstencao, teste_cita_fonte):
        try:
            teste(prov); resultados.append("passou")
        except AssertionError:
            resultados.append("FALHOU")
    print(f"{prov.nome:<15} -> {dict(zip(['abstenção', 'cita fonte'], resultados))}")
```

Os dois provedores passam nos dois testes, e a classe `Assistente` não foi alterada. Esse é o objetivo. Se um terceiro provedor (por exemplo, um LLM real) falhar em um teste, o teste revela o **comportamento** do provedor, e a lógica da aplicação permanece estável. Para modelos reais, os testes devem ser tolerantes à variabilidade (por exemplo, verificar propriedades e usar várias execuções), e **não** exigir texto idêntico.

## 9.14 Verificando os nomes das bibliotecas

Como não houve chamada real, verificamos ao menos que os **nomes** usados nos adaptadores existem nas versões instaladas dos pacotes. Isso não prova que as chamadas funcionarão (depende de credenciais, rede, versões do serviço), mas evita erros de digitação e APIs inventadas.

import importlib

## 9.15 Exemplos resolvidos

### Exemplo 1 — Calculando as esperas do recuo

**Problema.** Com $t_0=2$ s, teto de 20 s e sem jitter, quais são as esperas antes das tentativas 2 a 6? Qual o tempo total de espera se todas falharem?

**Solução.** $t_k=\min(20,\ 2\cdot2^{k})$ para $k=0,1,2,\ldots$: $2$; $4$; $8$; $16$; $\min(20,32)=20$. A soma é $2+4+8+16+20=50$ s de espera, além do tempo de cada tentativa.

**Interpretação.** O teto evita esperas enormes; mas o tempo total precisa caber no limite tolerado pelo usuário (daí o "tempo limite global").

### Exemplo 2 — Uma chave vazou

**Problema.** Um desenvolvedor percebe que fez *commit* de uma chave de API em um repositório privado há dois dias. Que passos seguir?

**Solução.** (1) **Revogar/rotacionar** a chave no provedor imediatamente; (2) gerar nova chave e armazenar em segredo gerenciado; (3) verificar o painel de uso do provedor por atividade anômala; (4) remover a chave do código e, se necessário, do histórico (reescrita de histórico não substitui a revogação); (5) adicionar varredura de segredos ao processo; (6) registrar o incidente e as lições.

**Interpretação.** Mesmo em repositório "privado", assuma que o segredo foi exposto: o custo de rotacionar é pequeno comparado ao de uma fatura indevida ou do acesso não autorizado.

### Exemplo 3 — Memória para atender 20 usuários

**Problema.** Um modelo local hipotético de 7 bilhões de parâmetros em 4 bits (≈3,5 GB) tem 32 camadas, 8 cabeças KV de 128 dimensões, `float16` no cache. Quanta memória é necessária para 20 usuários simultâneos com 4 096 tokens cada?

**Solução.** Cache por usuário: $2\times32\times4\,096\times8\times128\times2\approx0{,}54$ GB. Para 20 usuários: $\approx10{,}7$ GB. Total com pesos: $\approx3{,}5+10{,}7=14{,}2$ GB, sem ativações. Cabe em 24 GB com folga, mas não em 16 GB com margem de 15%.

**Interpretação.** O cache pode superar o tamanho dos pesos quando há muitos usuários: dimensionar só pelos pesos subestima a necessidade.

## 9.16 Atividade prática

**Objetivo.** Construir uma pequena aplicação com arquitetura em camadas, robusta e testável.

**Passo a passo.**

1. Defina a interface `ProvedorLLM` e implemente dois provedores simulados com comportamentos diferentes.
2. Implemente a classe de aplicação (recuperação, montagem de prompt, validação) dependente apenas da interface.
3. Acrescente recuo exponencial com `dormir` injetável, e teste com um provedor que falha as duas primeiras vezes.
4. Acrescente mascaramento de dados pessoais na entrada e validação com `pydantic` na saída.
5. Registre cada chamada em JSON Lines (sem texto integral) e calcule métricas simples a partir do log.
6. Escreva ao menos cinco testes automáticos que não usem rede.
7. (Opcional) Se você tiver acesso a um serviço ou a um modelo local, escreva um adaptador conforme a documentação oficial, **sem** colocar credenciais no código, e rode os mesmos testes, registrando versão do modelo, data e parâmetros.

## 9.17 Erros frequentes

- **Credenciais no código** ou em arquivos versionados.
- **Chamadas ao provedor espalhadas** pela aplicação.
- **Repetir erros permanentes** e **não repetir erros transitórios.**
- **Empilhar novas tentativas** (SDK e código próprio) multiplicando espera e carga.
- **Sem tempo limite** nas chamadas (processos que travam).
- **Sem orçamento** de tokens/custo e sem limite de concorrência.
- **Registrar texto sensível em logs** sem necessidade nem controle.
- **Fixar nomes de modelos no código**, em vez de configuração.
- **Confiar na saída sem validar.**
- **Testar apenas com o serviço real**, o que deixa os testes lentos, caros e instáveis.
- **Presumir que o parâmetro X existe em todos os modelos.**

## 9.18 Limitações e cuidados

- Os **adaptadores para serviços reais e modelos locais não foram executados**. Verificamos apenas a existência dos nomes nas versões instaladas; a correção das chamadas depende da documentação vigente, de credenciais e da rede.
- O **provedor simulado** extrai frases por similaridade de palavras. Não é um LLM e não representa suas falhas (respostas inventadas, variabilidade).
- O **mascaramento por expressões regulares** é insuficiente como proteção de privacidade; serve de ilustração.
- O recuo exponencial e o disjuntor mostrados são **versões didáticas**; bibliotecas maduras e os SDKs oferecem implementações mais completas.
- **Licenças, preços, limites e versões** de modelos e serviços mudam; tudo o que é volátil deve ser **conferido** na documentação oficial no momento do uso.

## 9.19 Síntese

:::lembrar O que vale a pena lembrar
- Uma aplicação com LLM tem etapas: preparar a entrada, chamar, validar, tratar falhas e registrar.
- **Portas e adaptadores:** a lógica depende de uma **interface**; cada provedor é um adaptador. Isso permite trocar de provedor e testar sem rede.
- **Erros transitórios** (rede, 429, 5xx, tempo esgotado) pedem **nova tentativa com recuo exponencial e jitter**; **erros permanentes** (400, 401, 403, 404) não.
- Use **tempo limite**, **orçamento**, **limite de concorrência**, **disjuntor** e **plano B**.
- **Modelos locais:** memória $\approx$ pesos $+$ cache KV; "pesos disponíveis" não é "modelo aberto"; **leia a licença**.
- **Mascare** dados pessoais, **limite** tokens com o tokenizador certo e **valide** saídas em três níveis.
- **Credenciais:** nunca no código; variáveis de ambiente ou gerenciador de segredos; menor privilégio; rotação; revogar ao vazar.
- **Registre** versão do prompt, modelo, parâmetros, tokens, latência e status (com cuidado de privacidade).
:::
