## 8.1 Situação inicial

Duas pessoas pedem a um assistente a mesma coisa. A primeira escreve: "Resuma esse contrato." A segunda escreve: "Você é um analista jurídico. Resuma o contrato abaixo em até cinco tópicos. Para cada tópico, cite entre aspas o trecho original que o sustenta. Se uma informação não constar no texto, escreva 'não consta'. Contrato: <<<...>>>".

O primeiro recebe um texto fluente, de tamanho e foco imprevisíveis. A segunda recebe tópicos curtos, cada um com uma citação que ela pode **conferir** no contrato. Nenhum dos dois sabe como o modelo funciona por dentro. A diferença está na **especificação**: a segunda pessoa disse o que queria, para quem, com que limites, em que formato e como verificar.

A **engenharia de prompts** é essa disciplina: escrever, testar e manter instruções para modelos de linguagem. Ela não é mágica, nem uma lista de "frases secretas". É especificação de requisitos, aplicada a um sistema probabilístico.

Como transformar um pedido vago em uma especificação que produza resultados **úteis, verificáveis e mensuráveis**, e como saber, com dados, se uma versão do prompt é de fato melhor que outra?
:::

## 8.5 O que é um prompt

Um **prompt** é o texto de entrada que condiciona a geração (Capítulo 6). Em aplicações, ele raramente é uma única frase: é um **documento montado** por código a partir de partes.

| Componente | Função | Exemplo |
|---|---|---|
| **Papel / instruções do sistema** | Define o comportamento geral | "Você é um assistente da secretaria acadêmica." |
| **Tarefa** | O que fazer | "Classifique a mensagem em uma das categorias abaixo." |
| **Contexto** | Informação de que o modelo precisa | Trechos do regulamento; histórico da conversa |
| **Exemplos** | Mostram o formato e o critério | Três mensagens com a categoria correta |
| **Entrada** | O dado a processar | A mensagem do cliente |
| **Formato de saída** | Como responder | "Responda apenas com JSON: {\"intencao\": ...}" |
| **Restrições** | Limites e regras | "Se não houver informação, responda 'não consta'." |

![f08_anatomia]([C] Anatomia de um prompt montado por código: cada componente pode ser testado, versionado e substituído de forma independente.)

:::cuidado Cuidado com esta interpretação
Um prompt **não** programa o modelo como código programa um computador. Ele **condiciona** uma distribuição de probabilidade. Por isso o mesmo prompt pode ter efeitos diferentes em modelos diferentes, ou na mesma versão em momentos diferentes, e **instruções não são garantias**: o modelo pode ignorá-las, interpretá-las mal ou obedecê-las apenas na maior parte das vezes. A consequência prática é que **todo prompt é uma hipótese a ser testada**.
:::

## 8.6 Objetivos, contexto, instruções e restrições

### 8.6.1 Princípios de especificação

1. **Diga o objetivo e o critério de sucesso.** "Resuma" é vago; "resuma em até 5 tópicos para um gestor, destacando prazos e valores" é verificável.
2. **Forneça o contexto necessário, e só ele.** O modelo não conhece sua empresa, seus documentos ou a data de hoje. Informação irrelevante gasta a janela de contexto e pode distrair.
3. **Seja específico sobre o formato.** Tamanho, estrutura, idioma, nível de detalhe, público.
4. **Prefira dizer o que fazer a dizer o que não fazer.** Instruções negativas isoladas ("não seja prolixo") funcionam pior que positivas ("responda em até 3 frases").
5. **Permita a abstenção.** Diga o que fazer quando faltar informação ("responda 'não consta'"), para reduzir respostas inventadas.
6. **Separe instruções de dados** com delimitadores claros.
7. **Peça evidências** quando a correção importa (Seção 8.9).
8. **Peça uma coisa de cada vez** quando possível (Seção 8.9).

### 8.6.2 Reescrevendo um prompt vago

| Versão | Prompt | Problemas |
|---|---|---|
| Vaga | "Classifique esta mensagem." | Não define categorias, formato nem o que fazer se nenhuma servir |
| Melhor | "Classifique a mensagem do cliente em **uma** das categorias: segunda_via, cancelamento, suporte_tecnico, alteracao_cadastro, rastreio_pedido, elogio, reclamacao, duvida_plano. Se nenhuma servir, responda `indefinido`." | Categorias e abstenção definidas, falta formato |
| Melhor ainda | "[...categorias...] **Responda apenas com JSON** no formato `{\"intencao\": \"<categoria>\", \"evidencia\": \"<trecho literal da mensagem>\"}`. Mensagem: <<<{mensagem}>>>" | Formato verificável; evidência checável |

O código a seguir monta o prompt a partir de componentes, o que torna cada parte **testável e versionável** (Seção 8.12).

```python
import hashlib
import json

CATEGORIAS = ["segunda_via", "cancelamento", "suporte_tecnico", "alteracao_cadastro", "rastreio_pedido", "elogio", "reclamacao", "duvida_plano"]

def montar_prompt(mensagem, papel=True, categorias=True, formato_json=True, exemplos=()):
    partes = []
    if papel:
        partes.append("Você é um assistente de triagem de mensagens de atendimento ao cliente.")
    tarefa = "Classifique a mensagem do cliente"
    tarefa += f" em UMA das categorias: {', '.join(CATEGORIAS)}. Se nenhuma servir, use 'indefinido'." if categorias else "."
    partes.append(tarefa)
    for msg, cat in exemplos:
        partes.append(f"Exemplo:\nMensagem: <<<{msg}>>>\nResposta: {json.dumps({'intencao': cat}, ensure_ascii=False)}")
    if formato_json:
        partes.append('Responda apenas com JSON: {"intencao": "<categoria>", "evidencia": "<trecho literal da mensagem>"}')
    partes.append(f"Mensagem: <<<{mensagem}>>>")
    return "\n\n".join(partes)

p = montar_prompt("quero cancelar meu plano hoje", exemplos=[("a fatura não chegou", "segunda_via")])
print(p)
print("\nidentificador do prompt (hash curto):", hashlib.sha1(p.encode("utf-8")).hexdigest()[:10])
print("número de caracteres:", len(p))
```

## 8.7 Exemplos no prompt

Quando descrever a tarefa não basta, **mostre** exemplos. Brown et al. (2020) chamam de ***zero-shot*** o uso sem exemplos, ***one-shot*** com um e ***few-shot*** com poucos, e mostram que o desempenho de modelos grandes tende a melhorar com exemplos, sem alterar os parâmetros (aprendizagem em contexto, Capítulo 1).

### 8.7.1 Como escolher exemplos

- **Representatividade.** Cubra as categorias e os casos difíceis; evite só exemplos fáceis.
- **Formato idêntico ao de saída desejado.** O modelo imita o formato dos exemplos.
- **Equilíbrio de rótulos.** Se quase todos os exemplos têm o mesmo rótulo, o modelo tende a repeti-lo.
- **Diversidade de redação.** Exemplos muito parecidos ensinam pouco.
- **Corretude.** Um exemplo errado ensina o erro.
- **Custo.** Cada exemplo ocupa tokens (latência e custo).

### 8.7.2 Sensibilidade à ordem e ao formato

Os resultados com exemplos podem depender da **ordem**, do **rótulo mais frequente** e do **último exemplo** (Zhao et al., 2021; Lu et al., 2022): permutações dos mesmos exemplos podem mudar muito a acurácia em alguns modelos. Duas implicações: (1) não conclua nada de uma única ordem; (2) teste algumas ordens e relate a variação.

## 8.8 Estruturação de entradas

Um prompt longo precisa de **estrutura**. Algumas práticas úteis:

- **Delimitadores** claros entre instruções e dados (`<<<` `>>>`, cercas de código, tags como `<documento>`...`</documento>`). Isso evita que o modelo confunda dados com instruções e é a primeira (e insuficiente) defesa contra a injeção de prompts (Perez; Ribeiro, 2022; Capítulo 17).
- **Seções nomeadas**: "Contexto", "Tarefa", "Formato".
- **Ordem**: coloque instruções importantes no início e repita o essencial no fim, quando o documento é longo; lembre que informação no meio de contextos longos pode ser menos usada (Liu et al., 2024).
- **Uma tarefa por prompt**, sempre que possível.
- **Dados em formato estável**: tabelas e listas com cabeçalhos consistentes.

```python+
def montar_prompt_documentos(pergunta, documentos):
    corpo = "\n".join(f"<documento id=\"{i}\">\n{t}\n</documento>" for i, t in documentos)
    return (
        "Responda à pergunta usando APENAS os documentos abaixo. Cite o id do documento que sustenta a resposta. "
        "Se a resposta não estiver nos documentos, responda exatamente: não consta.\n\n"
        f"{corpo}\n\nPergunta: {pergunta}\nResposta:"
    )

from llmdidatico import DOCS
print(montar_prompt_documentos("Qual a multa por atraso?", [(DOCS[11][0], DOCS[11][3])]))
```

## 8.9 Decomposição de tarefas e justificativas verificáveis

### 8.9.1 Dividir para conferir

Tarefas complexas funcionam melhor quando **divididas** em etapas, cada uma com entrada, saída e verificação próprias (**encadeamento de prompts**, *prompt chaining*). Exemplo: (1) extrair os fatos relevantes; (2) validar a extração por regras; (3) redigir a resposta usando **somente** os fatos validados. Benefícios: cada etapa é mais simples, testável e depurável; erros são localizados. Custo: mais chamadas, mais latência.

### 8.9.2 Raciocínio explícito, com cautela

Pedir ao modelo que "pense passo a passo" (***chain of thought***) melhorou o desempenho de modelos grandes em problemas de raciocínio aritmético e lógico (Wei et al., 2022), e amostrar vários raciocínios e votar na resposta mais frequente (***self-consistency***) melhora ainda mais (Wang et al., 2023). Mas há uma ressalva importante: **a explicação escrita pelo modelo não é um acesso fiel ao seu processo interno.** Turpin et al. (2023) mostraram que as explicações em cadeia de pensamento podem ser influenciadas por fatores que o texto **não menciona** (como a ordem das opções ou uma sugestão no prompt), e que podem justificar de modo plausível uma resposta determinada por outros motivos. Explicações geradas são **mais texto gerado**, e podem estar certas ou erradas.

### 8.9.3 O que pedir no lugar: justificativas verificáveis

Em vez de confiar na "explicação", peça **artefatos que você possa checar** de modo independente:

| Em vez de... | Peça... | Como verificar |
|---|---|---|
| "Explique por que" | **Citação literal** do trecho da fonte que sustenta a resposta | Procurar a citação no documento (busca de texto) |
| "Calcule" | **O cálculo explícito**, com os números usados | Refazer a conta em código |
| "Confie em mim" | **Evidências estruturadas**: lista de fatos com origem | Conferir cada fato e sua origem |
| "Tenho certeza" | **Abstenção quando faltar informação** | Testar com perguntas sem resposta |
| Resposta de múltiplas etapas | **Resultado de cada etapa** em campos separados | Validar cada campo por regra |

![f08_verif]([C] Em vez de confiar na explicação, verifica-se cada artefato que o modelo entrega: citações, cálculos, campos estruturados e abstenções.)

A ideia é transformar uma explicação (difícil de avaliar) em uma **afirmação checável**. O código a seguir verifica automaticamente se uma citação existe no documento e se um cálculo está correto. As "respostas do modelo" abaixo são **ilustrativas** (escritas à mão), com o objetivo de mostrar o verificador funcionando.

```python+
import re
import unicodedata

def normalizar(s):
    s = unicodedata.normalize("NFC", s).lower()
    return re.sub(r"\s+", " ", s).strip()

def citacao_existe(citacao, documento):
    return normalizar(citacao) in normalizar(documento)

doc = DOCS[11][3]     # documento sobre multas da biblioteca
respostas = [
    {"resposta": "R$ 1,50 por dia e por exemplar", "citacao": "multa de R$ 1,50 por dia e por exemplar"},
    {"resposta": "R$ 2,00 por dia", "citacao": "multa de R$ 2,00 por dia"},                       # citação inventada
    {"resposta": "suspensão ao passar de R$ 30,00", "citacao": "Quando a dívida passa de R$ 30,00, o empréstimo é suspenso"},
]
for r in respostas:
    print(f"citação verificada={citacao_existe(r['citacao'], doc)!s:<5} | resposta: {r['resposta']}")

def conferir_calculo(atraso_dias, exemplares, multa_dia, total_informado, tol=0.01):
    esperado = atraso_dias * exemplares * multa_dia
    return abs(esperado - total_informado) <= tol, esperado

for total in (31.50, 21.00):
    ok, esp = conferir_calculo(atraso_dias=7, exemplares=3, multa_dia=1.50, total_informado=total)
    print(f"total informado R$ {total:.2f} | esperado R$ {esp:.2f} | correto={ok}")
```

A segunda resposta tem uma citação que **não está** no documento: um alarme útil de resposta inventada. O cálculo informado de R$ 21,00 está errado (o correto é $7\times3\times1{,}50=31{,}50$). Nada disso exige confiar na "explicação" do modelo: verificamos os **artefatos**.

:::lembrar Regra prática
Peça justificativas que um **programa** (ou uma pessoa com a fonte aberta) possa verificar. Se a verificação for impossível, trate a justificativa como texto de apoio, e não como prova.
:::

## 8.10 Saídas estruturadas

Aplicações precisam de saídas **legíveis por máquina**. O padrão mais comum é pedir **JSON** com campos definidos e **validar** a resposta antes de usá-la. Pontos de atenção:

- **Esquema explícito**: campos, tipos, valores permitidos (enumerações), opcionais, e como indicar ausência (`null`).
- **Validação programática**: nunca confie que a resposta seja JSON válido ou obedeça ao esquema.
- **Novas tentativas controladas**: em caso de falha, reenvie ao modelo o erro de validação, com **limite** de tentativas.
- **Decodificação restrita**: alguns serviços e bibliotecas oferecem geração restrita a um esquema, o que reduz falhas de formato; consulte a documentação do serviço (não executado aqui).
- **Formato não é verdade**: uma saída que obedece ao esquema **pode** conter valores errados. Valide também o conteúdo (regras, citações).

```python+
import json
from typing import Optional, Literal
from pydantic import BaseModel, ValidationError, Field
import pydantic
print("versão do pydantic:", pydantic.VERSION)

class Extracao(BaseModel):
    intencao: Literal["segunda_via", "cancelamento", "suporte_tecnico", "alteracao_cadastro", "rastreio_pedido", "elogio", "reclamacao", "duvida_plano", "indefinido"]
    evidencia: Optional[str] = Field(default=None, max_length=200)

def validar(texto):
    try:
        return Extracao.model_validate_json(texto), None
    except (ValidationError, ValueError) as e:
        return None, str(e).splitlines()[0]

saidas = [
    '{"intencao": "cancelamento", "evidencia": "quero cancelar"}',   # válida
    '{"intencao": "cancelar", "evidencia": "quero cancelar"}',        # valor fora da enumeração
    'Claro! Aqui está o JSON: {"intencao": "elogio"}',                # texto extra antes do JSON
    '{"intencao": "elogio"}',                                         # válida, sem evidência
]
for s in saidas:
    obj, erro = validar(s)
    print("OK  " if obj else "FALHA", "|", s[:55].ljust(55), "|", obj.intencao if obj else erro[:60])
```

Observe a terceira saída: o modelo "educadamente" acrescentou texto antes do JSON, e a validação a rejeita. Em produção, isso é frequente. Uma tática é instruir "responda **apenas** com JSON", validar e, se falhar, tentar de novo com a mensagem de erro, no máximo duas ou três vezes, antes de encaminhar o caso a um tratamento alternativo.

```python+
def com_novas_tentativas(gerar, max_tentativas=3):
    """gerar(erro_anterior) -> texto. Retorna (objeto, tentativas, histórico de erros)."""
    erros, erro = [], None
    for k in range(1, max_tentativas + 1):
        texto = gerar(erro)
        obj, erro = validar(texto)
        if obj:
            return obj, k, erros
        erros.append(erro)
    return None, max_tentativas, erros

respostas_simuladas = iter(['Claro! {"intencao": "elogio"}', '{"intencao": "elogio", "evidencia": "parabéns"}'])
obj, k, erros = com_novas_tentativas(lambda e: next(respostas_simuladas))
print("objeto:", obj, "| tentativas:", k, "| erros intermediários:", len(erros))
```

## 8.11 Critérios de revisão

Para melhorar a qualidade, é comum pedir uma **segunda passada**: o próprio modelo (ou outro) revisa a resposta segundo critérios explícitos. Dois cuidados:

- **Critérios concretos.** "Verifique se todo número da resposta aparece no texto-fonte" é verificável; "melhore a resposta" não.
- **Revisão por modelo não é verificação independente.** Modelos podem aprovar respostas erradas e rejeitar corretas, e favorecem textos parecidos com os seus (Zheng et al., 2023). Sempre que possível, use **verificações programáticas** (como as da Seção 8.9) e **revisão humana** em casos de risco.

Uma lista de verificação (*checklist*) para revisar um prompt:

- [ ] O objetivo e o critério de sucesso estão explícitos?
- [ ] O contexto necessário foi fornecido, sem excesso?
- [ ] O formato de saída é especificado e validável?
- [ ] Há instrução sobre o que fazer quando faltar informação?
- [ ] Instruções e dados estão separados por delimitadores?
- [ ] Os exemplos são representativos, corretos e consistentes?
- [ ] A justificativa pedida é verificável?
- [ ] Há um conjunto de testes para este prompt?

## 8.12 Avaliação e versionamento de prompts

### 8.12.1 Prompts são código

Trate prompts como **artefatos de software**:

- **Versão**: identificador (número ou hash) e registro de mudanças.
- **Teste**: um conjunto de casos de teste com saídas esperadas, incluindo casos difíceis e sem resposta.
- **Métricas**: acerto (acurácia, F1), validade de formato, taxa de abstenção correta, custo e latência.
- **Comparação controlada**: mesma amostra de teste, mesmos parâmetros, uma mudança por vez.
- **Incerteza**: intervalo de confiança; evitar concluir por diferenças pequenas.
- **Regressão**: reexecutar os testes após cada mudança de prompt ou de modelo.

### 8.12.2 Um laço de avaliação (com o simulador)

Vamos avaliar três versões de prompt para a classificação de intenções, usando o `SimuladorLLM`. Lembre: os efeitos foram programados; o que interessa é o **processo**.

- **v1:** prompt vago (sem categorias nem formato).
- **v2:** categorias definidas e formato "rotulo: X".
- **v3:** categorias, exemplos e saída em JSON.

```python+
import numpy as np
from llmdidatico import corpus, avaliacao as av
from llmdidatico.simulador import SimuladorLLM, INTENCOES

def interpretar(versao, texto_resposta):
    """Extrai o rótulo da resposta conforme o formato esperado de cada versão; devolve (rótulo, formato_valido)."""
    if versao == "v3":
        obj, _ = validar(texto_resposta)
        return (obj.intencao, True) if obj else (None, False)
    if versao == "v2":
        m = re.fullmatch(r"rotulo: (\w+)", texto_resposta.strip())
        return (m.group(1), True) if m else (None, False)
    achados = [c for c in INTENCOES if c.replace("_", " ") in texto_resposta]
    return (achados[0], False) if achados else (None, False)       # v1: formato livre, nunca "válido"

X, y = corpus.intencoes(60, seed=11)          # 480 mensagens de teste (semente diferente da usada nos exemplos)
resultados = {}
print(f"{'versão':<7} {'acerto':>7} {'IC95% (bootstrap)':>20} {'formato válido':>15}")
for v in ("v1", "v2", "v3"):
    sim = SimuladorLLM(v, semente=0)
    acertos, validos = [], []
    for texto, rotulo in zip(X, y):
        pred, ok = interpretar(v, sim.responder(texto))
        acertos.append(float(pred == rotulo)); validos.append(float(ok))
    m, lo, hi = av.bootstrap_ic(acertos, n=1000, seed=0)
    resultados[v] = np.array(acertos)
    print(f"{v:<7} {m:>7.3f} {f'[{lo:.3f}; {hi:.3f}]':>20} {np.mean(validos):>15.3f}")

dif = resultados["v3"] - resultados["v2"]
m, lo, hi = av.bootstrap_ic(dif, n=1000, seed=0)
print(f"\ndiferença pareada v3 - v2: {m:+.3f}  IC95% [{lo:+.3f}; {hi:+.3f}]")
```

![f08_resultados]([D:figs_cap08.py] Acerto de três versões de prompt avaliadas com o simulador de regras, com intervalos de confiança de 95% por bootstrap. Os efeitos foram programados no simulador; o gráfico ilustra o formato do relatório, e não o desempenho de LLMs.)

O quadro mostra três coisas que um bom processo de avaliação deve mostrar: (1) o **acerto** de cada versão, com **intervalo de confiança**; (2) a **validade de formato**, que é uma métrica separada (um prompt pode acertar o conteúdo e falhar no formato); (3) a **diferença pareada** entre versões, com seu intervalo: se o intervalo inclui zero, a diferença pode ser acaso.

### 8.12.3 Registro da execução

Registre, para cada avaliação: identificador e versão do prompt, modelo e versão, data, parâmetros (temperatura, top-p, limite de tokens, semente quando houver), conjunto de teste (versão e tamanho) e métricas. ## 8.13 Exemplos resolvidos

### Exemplo 1 — Reescrevendo um pedido vago

**Problema.** Reescreva "Me ajuda com esse e-mail do cliente" para uma especificação verificável. Contexto: a secretaria quer um rascunho de resposta a um e-mail de reclamação sobre atraso de entrega.

**Solução.** "Você redige respostas da secretaria acadêmica. Abaixo está o e-mail de um aluno. (1) Resuma o problema em uma frase. (2) Redija um rascunho de resposta em até 120 palavras, em tom cordial, sem prometer prazos que não constem no texto de política abaixo. (3) Liste entre aspas os trechos da política em que você se baseou. Se a política não cobrir o caso, escreva 'não consta' e sugira encaminhar a um atendente. E-mail: <<<...>>> Política: <<<...>>>"

**Interpretação.** O novo pedido define papel, passos, tamanho, tom, restrição, evidência checável e abstenção. Cada elemento pode ser verificado (contagem de palavras, citações na política).

### Exemplo 2 — Interpretando uma comparação de prompts

**Problema.** Em 100 casos, o prompt A acerta 78 e o B acerta 84. Podemos afirmar que B é melhor?

**Solução.** Com 100 casos, o erro-padrão de uma proporção em torno de 0,8 é $\sqrt{0{,}8\times0{,}2/100}=0{,}04$, e o intervalo de 95% de cada acerto tem largura em torno de ±8 pontos percentuais. A diferença de 6 pontos está **dentro** dessa incerteza. Além disso, como A e B foram avaliados nos mesmos casos, o correto é calcular a diferença **pareada** (caso a caso) e seu intervalo.

**Interpretação.** Sem mais casos ou uma análise pareada, a evidência é fraca. Aumentar a amostra (por exemplo, para 500) e repetir com outras sementes é o caminho.

### Exemplo 3 — Falha de formato

**Problema.** Um sistema espera `{"prazo_dias": 30}`, mas o modelo responde `{"prazo_dias": "30 dias"}` em 12% dos casos. O que fazer?

**Solução.** (1) Tornar o esquema explícito no prompt, com exemplo e tipo (`inteiro`); (2) validar com um esquema (`pydantic`) e converter só quando seguro; (3) reenviar o erro ao modelo em uma nova tentativa, limitada; (4) medir a taxa de falha depois da mudança; (5) se persistir, considerar geração restrita a esquema, se o serviço oferecer.

**Interpretação.** Falhas de formato são esperadas e tratáveis, desde que medidas e tratadas por código, e não por esperança.

## 8.14 Atividade prática

**Objetivo.** Construir e avaliar três versões de um prompt para uma tarefa de sua escolha, com conjunto de testes e registro.

**Passo a passo.**

1. Escolha uma tarefa simples com resposta verificável (por exemplo, classificar mensagens, extrair datas e valores de textos curtos).
2. Escreva 30 casos de teste com a resposta esperada, incluindo 5 casos sem resposta e 5 difíceis.
3. Escreva três versões do prompt: (v1) vaga, (v2) com instruções, formato e abstenção, (v3) com exemplos.
4. Execute em um modelo à sua escolha (local ou por serviço), **registrando** modelo, versão, data e parâmetros. Se possível, repita 3 vezes.
5. Calcule acerto, validade de formato e taxa de abstenção correta, com intervalos de confiança.
6. Escreva um parágrafo discutindo se a diferença entre versões é distinguível do acaso e quais limites tem sua avaliação.

O Exercício prático 8.1 oferece uma versão com o simulador, para praticar o processo sem depender de serviços externos.

## 8.15 Erros frequentes

- **Tratar prompts como "encantamentos"**, procurando frases mágicas em vez de especificar.
- **Avaliar com poucos exemplos** e concluir pela melhor impressão.
- **Mudar vários elementos de uma vez**, sem saber o que causou a diferença.
- **Confiar na explicação** do modelo como prova da resposta.
- **Não validar o formato**, e deixar que saídas mal formadas quebrem o sistema.
- **Misturar instruções e dados sem delimitadores.**
- **Esquecer a abstenção**, empurrando o modelo a inventar.
- **Não versionar prompts**, perdendo o histórico do que funcionou.
- **Testar só casos fáceis.**
- **Ignorar a variabilidade** de geração.

## 8.16 Limitações e cuidados

- Os experimentos usam um **simulador de regras**, e não um LLM. Os efeitos observados (por exemplo, a melhora da v1 para a v3) foram **programados**; não generalize para modelos reais.
- As respostas de exemplo nas verificações de citação e de cálculo foram **escritas à mão** para ilustrar os verificadores.
- Os resultados de sensibilidade à ordem e de cadeia de pensamento vêm da literatura, para modelos e tarefas específicos; podem não se repetir em outros modelos.
- Recursos de serviços (modos de saída estruturada, instruções de sistema) variam entre provedores e mudam; consulte a documentação oficial vigente.
- Verificadores programáticos detectam apenas o que for especificado (existência de citação, cálculo): **uma resposta pode passar nas verificações e ainda estar errada**.

## 8.17 Síntese

:::lembrar O que vale a pena lembrar
- Um prompt é uma **especificação** montada por componentes: papel, tarefa, contexto, exemplos, entrada, formato e restrições.
- Prompts **condicionam** o modelo; não o programam. Toda versão é uma **hipótese a testar**.
- Exemplos ajudam, mas são sensíveis a **ordem, rótulos e formato**.
- Use **delimitadores** para separar instruções de dados; decomponha tarefas em etapas verificáveis.
- **Explicações geradas não são acesso fiel ao raciocínio interno.** Peça **citações literais, cálculos explícitos e evidências** que possam ser checados.
- **Saídas estruturadas** exigem esquema, **validação** e novas tentativas limitadas; formato válido não garante conteúdo correto.
- **Versione, teste e meça** prompts, com **intervalos de confiança** e comparações pareadas; registre modelo, data e parâmetros.
:::
