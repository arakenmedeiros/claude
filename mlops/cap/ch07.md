## 7.1 O modelo precisa sair do laboratório

Até aqui, o modelo vive em um notebook ou em um arquivo. Para gerar valor, alguém precisa **usá-lo**: um aplicativo, um sistema de cobrança, um analista com uma planilha. A etapa de **serviço** (*serving*) é a ponte entre o modelo e quem precisa das previsões.

Pense em um restaurante. A cozinha (treino) pode ser perfeita, mas se não houver **garçom, cardápio e balcão** (serviço), nenhum cliente é atendido. E o cardápio é um **contrato**: o cliente só pode pedir o que está nele.

## 7.2 Quatro formas de entregar previsões

A escolha da forma de entrega depende de **quando** a previsão é necessária e **quantas** são pedidas.

| Padrão | Como funciona | Latência | Exemplo |
|---|---|---|---|
| **Lote** (*batch*) | Roda em horários marcados sobre muitos registros e grava os resultados | Minutos a horas | Lista diária de clientes com risco de cancelar |
| **Tempo real** (*online*) | Um serviço responde a cada pedido individual | Milissegundos | Aprovar uma compra no cartão |
| **Fluxo contínuo** (*streaming*) | Processa eventos conforme chegam | Segundos | Detectar fraude em uma sequência de transações |
| **Embarcado** (*edge*) | O modelo roda no próprio dispositivo | Imediata, sem rede | Reconhecimento de voz no celular |

![f7_padroes](Figura 7.1 — Quatro padrões de serviço. Começar por lote costuma ser mais simples, barato e seguro; use tempo real quando a decisão realmente não pode esperar.)

:::dica Dica
Pergunte: "alguém precisa da resposta **agora**, ou amanhã de manhã serve?". Previsões em lote são muito mais fáceis de operar, e muitas decisões de negócio não exigem tempo real (HUYEN, 2022).
:::

## 7.3 O contrato de entrada e saída

Um serviço de previsão precisa deixar claro:

- **O que recebe:** campos, tipos, unidades, intervalos válidos.
- **O que devolve:** formato da resposta, versão do modelo, probabilidade ou classe.
- **Como falha:** códigos de erro e mensagens.

Em Python, a biblioteca **Pydantic** permite descrever esse contrato como uma classe. Os dados fora das regras são rejeitados **antes** de chegarem ao modelo.

```python
from typing import Literal
from pydantic import BaseModel, Field, ValidationError

class Cliente(BaseModel):
    idade: float = Field(ge=18, le=100)
    renda: float = Field(ge=0, le=1_000_000)
    tempo_cliente: float = Field(ge=0, le=600)
    plano: Literal["basico", "padrao", "premium"]
    cidade: Literal["Natal", "Recife", "Fortaleza"]

valido = Cliente(idade=33, renda=4500, tempo_cliente=8, plano="basico", cidade="Natal")
print("Entrada válida:", valido.model_dump())

for dados in [{"idade": -5, "renda": 4500, "tempo_cliente": 8, "plano": "basico", "cidade": "Natal"},
              {"idade": 30, "renda": 4500, "tempo_cliente": 8, "plano": "ultra", "cidade": "Natal"}]:
    try:
        Cliente(**dados)
    except ValidationError as e:
        erro = e.errors()[0]
        print("Rejeitada:", erro["loc"][0], "->", erro["msg"])
```

Esse contrato é a **primeira linha de defesa** contra dados ruins em produção, e também a documentação viva da API.

## 7.4 Uma API de previsão com FastAPI

O **FastAPI** é uma biblioteca moderna para criar serviços web em Python. Uma **API** (*Application Programming Interface*) é uma "porta de entrada" padronizada: outros programas enviam um pedido (por exemplo, os dados de um cliente) e recebem uma resposta (a previsão). A comunicação costuma usar o protocolo **HTTP** e o formato **JSON** (texto estruturado em chaves e valores).

Estes são os endereços (*endpoints*) que criaremos:

- `GET /saude`: responde se o serviço está vivo e qual modelo carregou.
- `POST /previsao`: recebe os dados de um cliente e devolve a probabilidade de cancelamento.

![f7_api](Figura 7.2 — Caminho de um pedido: o cliente envia JSON, o contrato valida, o pipeline prevê, e a resposta volta com a versão do modelo.)

Primeiro treinamos e salvamos um pipeline (o mesmo do Capítulo 4, com dados simulados de clientes):

```python
import joblib
import numpy as np
import pandas as pd
from sklearn.compose import ColumnTransformer
from sklearn.ensemble import RandomForestClassifier
from sklearn.impute import SimpleImputer
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

rng = np.random.default_rng(0)
n = 3000
df = pd.DataFrame({
    "idade": rng.integers(18, 75, n).astype(float),
    "renda": rng.lognormal(8, 0.5, n),
    "tempo_cliente": rng.integers(1, 120, n).astype(float),
    "plano": rng.choice(["basico", "padrao", "premium"], n, p=[0.5, 0.35, 0.15]),
    "cidade": rng.choice(["Natal", "Recife", "Fortaleza"], n),
})
risco = 0.03 * (50 - df["idade"]) - 0.02 * df["tempo_cliente"] + (df["plano"] == "basico") * 0.8
y = (risco + rng.normal(0, 0.8, n) > 0.3).astype(int)

num, cat = ["idade", "renda", "tempo_cliente"], ["plano", "cidade"]
prep = ColumnTransformer([
    ("num", Pipeline([("imp", SimpleImputer(strategy="median")), ("esc", StandardScaler())]), num),
    ("cat", OneHotEncoder(handle_unknown="ignore"), cat)])
pipe = Pipeline([("prep", prep),
                 ("modelo", RandomForestClassifier(n_estimators=100, random_state=0))]).fit(df[num + cat], y)
joblib.dump({"pipeline": pipe, "versao": "1.0.0", "colunas": num + cat}, "modelo.joblib")
print("Modelo salvo.")
```

Agora o serviço. Em um projeto real, este código ficaria em `src/servir.py`:

```python
# continuação (arquivo src/servir.py; no arquivo real, importe também joblib e pandas)
from contextlib import asynccontextmanager
from typing import Literal
from fastapi import FastAPI
from pydantic import BaseModel, Field


class Cliente(BaseModel):
    idade: float = Field(ge=18, le=100)
    renda: float = Field(ge=0, le=1_000_000)
    tempo_cliente: float = Field(ge=0, le=600)
    plano: Literal["basico", "padrao", "premium"]
    cidade: Literal["Natal", "Recife", "Fortaleza"]


class Resposta(BaseModel):
    probabilidade_cancelar: float
    versao_modelo: str


def criar_app(caminho="modelo.joblib"):
    estado = {}

    @asynccontextmanager
    async def ciclo_de_vida(app):
        estado["art"] = joblib.load(caminho)    # carrega UMA vez, na partida do serviço
        yield
        estado.clear()

    app = FastAPI(title="API de previsão de cancelamento", lifespan=ciclo_de_vida)

    @app.get("/saude")
    def saude():
        return {"status": "ok", "versao_modelo": estado["art"]["versao"]}

    @app.post("/previsao", response_model=Resposta)
    def prever(c: Cliente):
        art = estado["art"]
        linha = pd.DataFrame([c.model_dump()])[art["colunas"]]
        p = float(art["pipeline"].predict_proba(linha)[0, 1])
        return Resposta(probabilidade_cancelar=round(p, 4), versao_modelo=art["versao"])

    return app
```

Pontos importantes:

- O modelo é carregado **uma única vez**, na partida. Carregar a cada pedido seria lentíssimo.
- A resposta traz a **versão do modelo**, o que facilita a rastreabilidade.
- A API recebe a **linha crua**, e o pipeline cuida do pré-processamento, evitando o desvio treino–serviço.

Para executar de verdade, você usaria o servidor `uvicorn` (`uvicorn servir:app --port 8000`) e abriria `http://127.0.0.1:8000/docs`, onde o FastAPI gera uma página de documentação interativa.

## 7.5 Testando a API sem subir servidor

O FastAPI traz o `TestClient`, que simula pedidos HTTP **dentro do próprio programa**. Assim, a API é testada automaticamente a cada mudança (Capítulo 8).

```python
# continuação (arquivo tests/test_api.py)
from fastapi.testclient import TestClient

ok = {"idade": 33, "renda": 4500, "tempo_cliente": 8, "plano": "basico", "cidade": "Natal"}

with TestClient(criar_app()) as cliente:
    r = cliente.get("/saude")
    print("GET /saude        ->", r.status_code, r.json())

    r = cliente.post("/previsao", json=ok)
    print("POST /previsao    ->", r.status_code, r.json())

    r = cliente.post("/previsao", json=dict(ok, idade=-5))
    print("idade negativa    ->", r.status_code, r.json()["detail"][0]["msg"])

    r = cliente.post("/previsao", json=dict(ok, plano="ultra"))
    print("plano desconhecido->", r.status_code, r.json()["detail"][0]["type"])

    r = cliente.post("/previsao", json={"idade": 30})
    print("campos faltando   ->", r.status_code, f"({len(r.json()['detail'])} erros)")
```

O código **422** significa "entidade não processável": o pedido chegou, mas os dados violam o contrato. Veja que o modelo nem chegou a ser chamado. Esses testes ficam guardados e rodam sempre.

:::atencao Atenção
A API mostrada é didática. Em produção, acrescente **autenticação**, **limites de taxa**, **registro (log) estruturado** e **tratamento de exceções**, além de um serviço rodando com vários processos (*workers*) para atender pedidos em paralelo.
:::

## 7.6 Latência: não olhe só a média

**Latência** é o tempo entre o pedido e a resposta. Dizer "a latência média é 20 ms" esconde os piores casos. Imagine um restaurante em que a média de espera é 10 minutos, mas 1 em cada 100 clientes espera 1 hora. Esses clientes existem.

Por isso usamos **percentis**:

- **p50** (mediana): metade dos pedidos é mais rápida que isso.
- **p95:** 95% dos pedidos são mais rápidos que isso.
- **p99:** 99% dos pedidos são mais rápidos que isso (a "cauda").

A literatura de confiabilidade de sistemas (BEYER et al., 2016) recomenda acompanhar a distribuição, e não apenas a média. Combinados com o negócio, definem-se **objetivos de nível de serviço** (SLOs), como "p95 abaixo de 100 ms".

```python
import time
import numpy as np
from sklearn.datasets import load_breast_cancer
from sklearn.ensemble import RandomForestClassifier

X, y = load_breast_cancer(return_X_y=True)
modelo = RandomForestClassifier(n_estimators=200, random_state=0).fit(X, y)

tempos = []
for i in range(300):
    linha = X[i % len(X)].reshape(1, -1)
    t0 = time.perf_counter()
    modelo.predict_proba(linha)
    tempos.append((time.perf_counter() - t0) * 1000)       # em milissegundos

p50, p95, p99 = np.percentile(tempos, [50, 95, 99])
print(f"p50 = {p50:.1f} ms | p95 = {p95:.1f} ms | p99 = {p99:.1f} ms | média = {np.mean(tempos):.1f} ms")

# vazão: uma previsão por vez versus um lote de 300
t0 = time.perf_counter(); [modelo.predict_proba(X[i:i+1]) for i in range(300)]; um_a_um = time.perf_counter() - t0
t0 = time.perf_counter(); modelo.predict_proba(X[:300]); em_lote = time.perf_counter() - t0
print(f"300 previsões uma a uma: {um_a_um*1000:.0f} ms | em um lote só: {em_lote*1000:.0f} ms")
```

Os números exatos dependem do seu computador, mas o padrão se repete: **processar em lote é muito mais eficiente que um registro por vez**. Por isso, serviços de alto volume agrupam pedidos (*micro-batching*).

## 7.7 Contêineres: levando o ambiente junto

Lembra do "funciona na minha máquina"? Para o modelo rodar na máquina do servidor, é preciso reproduzir **o mesmo Python, as mesmas bibliotecas e o mesmo sistema**. Os **contêineres** resolvem isso.

Um **contêiner** é uma "marmita lacrada": ele leva dentro **o programa e tudo o que ele precisa para rodar**. Ao contrário de uma máquina virtual completa, compartilha o núcleo do sistema operacional do hospedeiro, sendo leve e rápido para iniciar (MERKEL, 2014). O **Docker** é a ferramenta mais conhecida para isso.

Três palavras-chave:

- **Imagem:** o "molde" da marmita (somente leitura).
- **Contêiner:** uma marmita em uso, criada a partir da imagem.
- **Dockerfile:** a receita que descreve como montar a imagem.

![f7_conteiner](Figura 7.3 — Camadas de uma imagem de contêiner: sistema base, Python, dependências, código e modelo. Camadas que mudam pouco ficam embaixo, para aproveitar o cache.)

Este é um `Dockerfile` típico para a nossa API:

```dockerfile
FROM python:3.13-slim

WORKDIR /app

# 1) dependências primeiro: esta camada só muda se o requirements.txt mudar
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 2) código e modelo depois
COPY src/ ./src/
COPY modelo.joblib .

# 3) boa prática: não rodar como administrador
RUN useradd --create-home appuser
USER appuser

EXPOSE 8000
CMD ["uvicorn", "src.servir:app", "--host", "0.0.0.0", "--port", "8000"]
```

E os comandos para construir e executar:

```bash
docker build -t api-churn:1.0.0 .             # constrói a imagem com um nome e versão
docker run -p 8000:8000 api-churn:1.0.0       # executa, expondo a porta 8000
curl http://127.0.0.1:8000/saude              # testa
```

:::atencao Atenção
O `Dockerfile` e os comandos acima são **ilustrativos** e não foram executados na elaboração deste livro (o ambiente de escrita não tinha o Docker). Em `src/servir.py` real, você precisaria também criar o objeto `app = criar_app()`. Teste no seu ambiente.
:::

### 7.7.1 Boas práticas com imagens

- Use uma **imagem base pequena** (`-slim`) e **versões fixas**, nunca `latest`.
- **Ordene as camadas** da que muda menos (dependências) para a que muda mais (código).
- **Não coloque segredos** (senhas, chaves) na imagem.
- Use um **usuário comum**, não o administrador.
- **Etiquete** a imagem com a versão do código e do modelo (rastreabilidade).
- Verifique **vulnerabilidades** das dependências.

## 7.8 Previsão em lote

Na previsão em lote, o programa lê muitos registros, prevê tudo e grava os resultados. O ponto crítico é a **idempotência**: se o trabalho rodar duas vezes por engano (ou for reexecutado após uma falha), o resultado deve ser **o mesmo**, sem duplicar registros.

Uma forma simples: gravar o resultado em um arquivo cujo nome depende da **data de referência** e **sobrescrevê-lo**, em vez de acrescentar linhas.

```python
import json
import os
import hashlib
import joblib
import numpy as np
import pandas as pd
from sklearn.datasets import load_wine
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler

# modelo de exemplo salvo
dados = load_wine(as_frame=True)
pipe = make_pipeline(StandardScaler(), LogisticRegression(max_iter=2000)).fit(dados.data, dados.target)
joblib.dump({"pipeline": pipe, "versao": "2.1.0"}, "modelo_lote.joblib")


def prever_em_lote(df_entrada, data_ref, pasta="saidas", tamanho_bloco=50):
    art = joblib.load("modelo_lote.joblib")
    os.makedirs(pasta, exist_ok=True)
    blocos = []
    for ini in range(0, len(df_entrada), tamanho_bloco):                # processa por blocos
        parte = df_entrada.iloc[ini:ini + tamanho_bloco]
        blocos.append(pd.DataFrame({
            "indice": parte.index,
            "classe_prevista": art["pipeline"].predict(parte),
            "versao_modelo": art["versao"],
            "data_ref": data_ref}))
    saida = pd.concat(blocos, ignore_index=True)
    caminho = os.path.join(pasta, f"previsoes_{data_ref}.csv")
    saida.to_csv(caminho, index=False)                                 # sobrescreve: idempotente
    return caminho


c1 = prever_em_lote(dados.data, "2026-10-17")
h1 = hashlib.sha256(open(c1, "rb").read()).hexdigest()[:12]
c2 = prever_em_lote(dados.data, "2026-10-17")                          # reexecução acidental
h2 = hashlib.sha256(open(c2, "rb").read()).hexdigest()[:12]
print("Arquivo:", c1, "| linhas:", len(pd.read_csv(c1)))
print("Reexecução gerou o mesmo resultado?", h1 == h2)
```

:::dica Dica
Em previsão em lote, **registre** o que foi previsto (versão do modelo, data de referência, número de linhas, hash da entrada). Será essencial para auditar e para monitorar o modelo (Capítulo 9).
:::

## 7.9 Estratégias de entrega: um panorama

Ao trocar o modelo em produção, é preciso evitar surpresas. Alguns padrões (aprofundados no Capítulo 9):

| Estratégia | Como funciona | Risco |
|---|---|---|
| **Substituição direta** | Troca o modelo de uma vez | Alto |
| **Azul-verde** (*blue-green*) | Dois ambientes idênticos; o tráfego passa do antigo (azul) para o novo (verde) | Baixo; reversão rápida |
| **Canário** (*canary*) | O modelo novo recebe uma pequena fração do tráfego | Baixo; limita o dano |
| **Sombra** (*shadow*) | O modelo novo recebe cópia do tráfego, mas suas respostas **não** são usadas | Muito baixo; compara em silêncio |

## 7.10 Segurança no serviço de modelos

Um modelo exposto na rede é uma porta de entrada. Cuidados mínimos:

- **Valide tudo** na entrada (tipos, intervalos, tamanho máximo do pedido).
- **Autentique** e **autorize** quem pode pedir previsões.
- **Limite a taxa** de pedidos para evitar abuso.
- **Guarde segredos** em um cofre, nunca no código ou na imagem.
- **Atualize dependências** e verifique vulnerabilidades.
- **Não exponha mais do que o necessário**: devolver probabilidades detalhadas, por exemplo, pode facilitar ataques de inferência de associação (SHOKRI et al., 2017), em que um atacante tenta descobrir se uma pessoa estava no conjunto de treino.
- **Registre** os acessos para auditoria, respeitando a privacidade.

- Escolha o padrão de entrega pelo prazo da decisão: **lote**, **tempo real**, **fluxo contínuo** ou **embarcado**. Lote é o mais simples.
- Defina um **contrato** de entrada e saída (Pydantic) para rejeitar dados ruins cedo.
- Em **FastAPI**: carregue o modelo uma vez, devolva a **versão** na resposta e teste com `TestClient`.
- Meça **percentis de latência** (p50, p95, p99), e não só a média. Lotes são mais eficientes que pedidos únicos.

- Em lote, garanta **idempotência** e registre a execução.
- **Segurança**: valide, autentique, limite a taxa, proteja segredos e atualize dependências.
:::
