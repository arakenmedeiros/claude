## 11.1 Além da classificação

Quase tudo que fizemos até aqui foi **classificar** (aprendizado supervisionado). Mas o aprendizado federado vai muito além:

- **Aprendizado não supervisionado:** agrupar, reduzir dimensões e descobrir padrões **sem rótulos**.
- **Análises federadas:** calcular estatísticas (médias, histogramas, contagens) sobre dados distribuídos sem juntá-los.
- **Modelos de fundação:** especializar grandes modelos de linguagem e de imagens com dados privados.

Vamos conhecer cada um, começando pelo mais simples.

:::cotidiano No seu dia a dia
Uma rede de lojas quer saber **quais perfis de cliente existem**, sem que cada loja entregue seu cadastro. Ninguém rotulou os clientes: o objetivo é **descobrir grupos**. É um problema não supervisionado, e dá para resolvê-lo de forma federada.
:::

## 11.2 K-means federado

O **K-means** divide os dados em *k* grupos. Em cada iteração (algoritmo de Lloyd):

1. cada ponto é atribuído ao **centroide mais próximo**;
2. cada centroide vira a **média** dos seus pontos.

A beleza: o passo 2 só precisa, para cada grupo, da **soma dos pontos** e da **contagem**. Essas são estatísticas que **se combinam por soma**, como a média e a variância do Capítulo 2.

**K-means federado:**

1. o servidor envia os *k* centroides;
2. cada cliente atribui seus pontos e devolve, por grupo, **(soma, contagem)**;
3. o servidor soma tudo e calcula os novos centroides.

O resultado é **idêntico** ao do K-means centralizado, com a mesma inicialização.

## 11.3 PCA federado

A **análise de componentes principais** (PCA) acha as direções de maior variação dos dados. Ela depende da **matriz de covariância**, que se calcula com somas:

$$ cov = ( Σ x xᵀ − n · μ μᵀ ) / ( n − 1 ) $$

Cada cliente envia *n*, *Σx* e *Σ x xᵀ*. O servidor soma, calcula a covariância e seus autovetores. De novo, o resultado é **exatamente o do PCA centralizado**.

## 11.4 A biblioteca `fronteiras.py`

Salve o código abaixo como **`fronteiras.py`**, ao lado da `fedlib.py`. Ele reúne o K-means e o PCA federados e o ajuste de adaptadores de baixo posto da seção 11.6.

```python
import numpy as np
from fedlib import *


# ------------------------------------------------------------------ K-means federado
def kmeans_federado(partes, X, centroides, iteracoes=30):
    """Algoritmo de Lloyd distribuído: cada cliente devolve, por grupo, a soma dos pontos e a contagem."""
    C = centroides.copy()
    for _ in range(iteracoes):
        S, N = np.zeros_like(C), np.zeros(len(C))
        for p in partes:                                   # (em um sistema real, isto roda em cada cliente)
            Xk = X[p]
            a = ((Xk[:, None, :] - C[None]) ** 2).sum(-1).argmin(1)
            for j in range(len(C)):
                S[j] += Xk[a == j].sum(0)
                N[j] += (a == j).sum()
        C = np.where(N[:, None] > 0, S / np.maximum(N, 1)[:, None], C)   # servidor: nova média de cada grupo
    return C


# ------------------------------------------------------------------ PCA federado
def pca_federado(partes, X, n_componentes):
    """PCA exato a partir de somas locais: cada cliente envia n, Σx e Σxxᵀ."""
    n, s, ss = 0, 0.0, 0.0
    for p in partes:
        Xk = X[p]
        n += len(Xk); s = s + Xk.sum(0); ss = ss + Xk.T @ Xk
    mu = s / n
    cov = (ss - n * np.outer(mu, mu)) / (n - 1)
    valores, vetores = np.linalg.eigh(cov)
    ordem = np.argsort(valores)[::-1][:n_componentes]
    return mu, valores[ordem], vetores[:, ordem]


# ------------------------------------------------------------------ Adaptadores de baixo posto (estilo LoRA)
def fedavg_adaptador(partes, X, y, Xte, yte, W0, posto, rodadas=20, epocas=3, eta=0.1, lote=32, seed=0):
    """Mantém W0 congelado e treina só ΔW = A·B, com A (d×r) e B (r×K). Só A e B trafegam.
    Com posto=None, treina o modelo inteiro (referência)."""
    rng = np.random.default_rng(seed)
    d, K = W0.shape
    A = rng.normal(0, 0.01, (d, posto)) if posto else None
    B = np.zeros((posto, K)) if posto else None
    W = W0.copy()
    bytes_por_rodada = 2 * 4 * (d * K if posto is None else posto * (d + K))
    historico = []
    for r in range(rodadas):
        locais, tam = [], []
        for c, p in enumerate(partes):
            if len(p) == 0:
                continue
            rk = np.random.default_rng(seed * 1000 + r * 50 + c)
            if posto is None:
                w = W.copy()
                for _ in range(epocas):
                    o = rk.permutation(len(p))
                    for i in range(0, len(p), lote):
                        b = p[o[i:i + lote]]; w -= eta * gradiente(w, X[b], y[b])
                locais.append(w)
            else:
                a, bb = A.copy(), B.copy()
                for _ in range(epocas):
                    o = rk.permutation(len(p))
                    for i in range(0, len(p), lote):
                        b = p[o[i:i + lote]]
                        G = gradiente(W0 + a @ bb, X[b], y[b])           # gradiente em relação a ΔW
                        a, bb = a - eta * G @ bb.T, bb - eta * a.T @ G   # regra da cadeia para A e B
                locais.append((a, bb))
            tam.append(len(p))
        pesos = np.array(tam) / sum(tam)
        if posto is None:
            W = sum(pi * wi for pi, wi in zip(pesos, locais)); acc = acuracia(W, Xte, yte)
        else:
            A = sum(pi * l[0] for pi, l in zip(pesos, locais)); B = sum(pi * l[1] for pi, l in zip(pesos, locais))
            acc = acuracia(W0 + A @ B, Xte, yte)
        historico.append(acc)
    return historico, bytes_por_rodada
```

## 11.5 Experimento: agrupar e comprimir sem juntar os dados

Usamos o conjunto *Wine*, da UCI, em **5 clientes muito desiguais** (distribuição de Dirichlet com α = 0,3). Comparamos com o `KMeans` e o `PCA` do scikit-learn aplicados aos dados juntos.

```python
import numpy as np
from sklearn.datasets import load_wine
from sklearn.preprocessing import StandardScaler
from sklearn.cluster import KMeans
from sklearn.decomposition import PCA
from sklearn.metrics import adjusted_rand_score
from fronteiras import *

X, y = load_wine(return_X_y=True)
X = StandardScaler().fit_transform(X)          # (didático; ver aviso do Capítulo 2 sobre padronização federada)
partes = particao_dirichlet(y, 5, 0.3, seed=0)
print("clientes (tamanhos):", [len(p) for p in partes])

# ---- K-means ----
rng = np.random.default_rng(0)
C0 = X[rng.choice(len(X), 3, replace=False)]                       # mesma inicialização para os dois
Cf = kmeans_federado(partes, X, C0, iteracoes=50)
km = KMeans(3, init=C0, n_init=1, max_iter=300, tol=0, algorithm="lloyd").fit(X)
rotulos_f = ((X[:, None, :] - Cf[None]) ** 2).sum(-1).argmin(1)
print("K-means: diferença máxima entre centroides:", float(np.abs(Cf - km.cluster_centers_).max()))
print("K-means: ARI entre federado e centralizado:", adjusted_rand_score(rotulos_f, km.labels_))
print("K-means: ARI do federado contra as classes reais:", round(adjusted_rand_score(y, rotulos_f), 3))

# ---- PCA ----
mu, valores, vetores = pca_federado(partes, X, 3)
pca = PCA(3).fit(X)
print("PCA: variâncias federadas   :", np.round(valores, 4))
print("PCA: variâncias centralizadas:", np.round(pca.explained_variance_, 4))
print("PCA: |cos| entre componentes :", np.round([abs(vetores[:, i] @ pca.components_[i]) for i in range(3)], 6))
```

![f11_kmeans](Figura 11.3 — Projeção dos vinhos nas duas primeiras componentes principais. À esquerda, cada ponto tem a cor do cliente que o possui (muito desiguais); à direita, o agrupamento federado, idêntico ao centralizado.)

Resultados: os centroides coincidem até a casa dos 10⁻¹⁶, o agrupamento federado é **idêntico** ao centralizado (ARI = 1), e as variâncias e direções do PCA são as mesmas.

:::memorize Memorize
Sempre que um algoritmo depende só de **somas de estatísticas locais** (médias, contagens, covariâncias), a versão federada é **exata**. Isso vale para K-means, PCA, regressão linear por mínimos quadrados e Naive Bayes.
:::

:::atencao Atenção
Somas e contagens por grupo **também vazam informação**, sobretudo em grupos pequenos (por exemplo, um grupo com um único cliente revela sua média exata). Combine com **agregação segura** e **privacidade diferencial** (Capítulo 8).
:::

## 11.6 Modelos de fundação e modelos de linguagem

### 11.6.1 O cenário

**Modelos de fundação** (*foundation models*) são modelos enormes pré-treinados com dados gerais e depois **especializados**. Muitos dos dados mais valiosos para especializá-los (prontuários, contratos, conversas de atendimento) são **privados** e não podem ser juntados. Daí o interesse em **ajustar modelos de linguagem de forma federada** (Ye et al., 2024; Kuang et al., 2024).

Os obstáculos são claros:

- **Tamanho:** bilhões de parâmetros. Enviar o modelo inteiro a cada rodada é inviável.
- **Memória e cálculo:** muitos clientes não conseguem sequer treinar o modelo completo.
- **Memorização:** modelos grandes decoram trechos do treino (Carlini et al., 2021).

### 11.6.2 A saída: ajuste eficiente em parâmetros

Em vez de treinar tudo, **congela-se** o modelo pré-treinado e treinam-se **poucos parâmetros extras**:

- **Adaptadores** (*adapters*): pequenas camadas inseridas no modelo (Houlsby et al., 2019).
- **LoRA** (*low-rank adaptation*): aprende uma correção de **baixo posto** nos pesos (Hu et al., 2022).

A ideia do LoRA: em vez de aprender uma correção Δ*W* com *d × K* números, aprendem-se duas matrizes pequenas, *A* (*d × r*) e *B* (*r × K*), com *r* pequeno, e usa-se

$$ W = W₀ + A · B $$

O número de parâmetros treináveis cai de *d·K* para *r·(d + K)*. Só *A* e *B* trafegam entre cliente e servidor. A economia de comunicação é enorme.

![f11_lora](Figura 11.1 — O modelo pré-treinado W₀ fica congelado. Cada cliente treina só as matrizes A e B, de baixo posto. Só elas trafegam.)

### 11.6.3 Um experimento em miniatura

Imitamos o cenário com um modelo pequeno. O "modelo de fundação" é uma softmax treinada com os dígitos (acurácia de 0,97). Aparece então uma **tarefa nova**: o mundo trocou os nomes de duas duplas de classes (3 ↔ 5 e 4 ↔ 9). O modelo antigo erra muito (acurácia 0,58). Vinte clientes (Dirichlet α = 0,5) ajustam o modelo, ou por completo, ou só com adaptadores de posto *r*.

```python
import numpy as np
from fronteiras import *

Xtr, Xte, ytr, yte = carregar_digits()

# "modelo de fundação": softmax treinada com os rótulos originais
W0 = np.zeros((65, 10))
for _ in range(300):
    W0 -= 0.5 * gradiente(W0, Xtr, ytr)
print(f"modelo pré-treinado, tarefa original : {acuracia(W0, Xte, yte):.3f}")

# tarefa nova: troca dos nomes 3<->5 e 4<->9
perm = np.arange(10); perm[3], perm[5] = 5, 3; perm[4], perm[9] = 9, 4
ytr2, yte2 = perm[ytr], perm[yte]
print(f"modelo pré-treinado, tarefa nova     : {acuracia(W0, Xte, yte2):.3f}")

print(f"\n{'método':<14}{'KB por rodada':>15}{'acc rodada 5':>14}{'acc rodada 20':>15}")
for nome, posto in [("completo", None), ("LoRA r=1", 1), ("LoRA r=2", 2), ("LoRA r=4", 4), ("LoRA r=8", 8)]:
    hs = []
    for s in range(3):
        partes = particao_dirichlet(ytr, 20, 0.5, seed=s)
        h, bytes_rodada = fedavg_adaptador(partes, Xtr, ytr2, Xte, yte2, W0, posto, seed=s)
        hs.append(h)
    h = np.mean(hs, axis=0)
    print(f"{nome:<14}{bytes_rodada / 1024:>15.1f}{h[4]:>14.3f}{h[-1]:>15.3f}")
```

![f11_lora_res](Figura 11.2 — Acurácia na tarefa nova contra o tráfego por cliente e rodada: o posto 2 já recupera o desempenho do ajuste completo com cerca de um quarto do tráfego; o posto 1 não basta.)

O que aprendemos:

- O **ajuste completo** chega a cerca de 0,95, trafegando **5,1 KB** por cliente e rodada.
- O **LoRA com posto 2** atinge **0,96**, com **1,2 KB** (4 vezes menos).
- No começo, os adaptadores são **mais lentos** (rodada 5: 0,66 contra 0,79 do ajuste completo), pois precisam de mais rodadas para aprender a correção.
- O **posto 1 não basta** (≈ 0,79): trocar duas duplas de classes exige uma correção de posto **pelo menos 2**. A capacidade do adaptador precisa casar com a tarefa.
- Em redes grandes, a diferença de tamanho é gigantesca (milhões contra bilhões de parâmetros).

:::atencao Atenção
Uma sutileza: a média de *A* e a média de *B* **não** são a média dos produtos *A·B*. A média das matrizes separadas introduz um erro de agregação. Métodos recentes tratam disso (por exemplo, agregando os produtos ou empilhando os adaptadores). No nosso experimento, o erro é pequeno, mas em modelos grandes merece atenção.
:::

:::saibamais Saiba mais
Outras ideias para modelos de fundação federados: **prompts** aprendidos (em vez de pesos), **destilação** (os clientes enviam previsões, e não pesos), **modelos pequenos locais com grandes remotos**, e o uso de **dados sintéticos** gerados pelo modelo para reduzir a exposição de dados reais. A área está em rápida evolução: consulte as publicações recentes.
:::

## 11.7 Ferramentas e frameworks

Para sair da simulação e construir sistemas reais, usam-se frameworks. Os principais são software livre.

| Ferramenta | Foco principal | Observações |
|---|---|---|
| **Flower** | Simulação e implantação, independente de biblioteca de ML | Suporta PyTorch, TensorFlow, scikit-learn |
| **TensorFlow Federated (TFF)** | Pesquisa e simulação com TensorFlow | Integra privacidade diferencial |
| **PySyft** | Privacidade e computação remota | Foco em ciência de dados com dados privados |
| **FATE** | Cross-silo industrial, incluindo vertical | Voltado a finanças e empresas |
| **FedML** | Pesquisa, simulação e implantação | Dispositivos móveis e nuvem |
| **NVIDIA FLARE** | Cross-silo, saúde e indústria | Foco em implantação |
| **OpenFL** | Cross-silo, saúde | Originado em colaborações médicas |
| **LEAF e FedScale** | Conjuntos de referência (*benchmarks*) | Para comparar algoritmos |

Para escolher, pergunte:

1. É **simulação** (pesquisa) ou **implantação** (produção)?
2. É **cross-device** ou **cross-silo**? É horizontal ou vertical?
3. Qual **biblioteca de ML** a equipe usa?
4. Que **garantias de segurança** são necessárias (agregação segura, DP, TEE)?
5. A ferramenta é **mantida ativamente** e tem comunidade?

:::atencao Atenção
Ferramentas mudam rápido. Antes de decidir, consulte a **documentação atual** e a licença de cada projeto. Este livro não valida versões específicas.

## 11.8 Aplicações reais

![f11_aplicacoes](Figura 11.4 — Quatro áreas de aplicação e o que cada uma protege ou combina.)

### 11.8.1 Saúde

É a área de maior destaque. Colaborações entre hospitais usaram aprendizado federado em imagens de tumores cerebrais (Sheller et al., 2020) e em previsão de necessidades de oxigênio na COVID-19 com dados de vinte instituições (Dayan et al., 2021). Rieke et al. (2020) e Xu et al. (2021) discutem oportunidades e obstáculos: dados muito heterogêneos entre hospitais, protocolos de imagem diferentes, governança e confiança.

### 11.8.2 Dispositivos móveis

Teclados, assistentes de voz e recomendações em celulares. O sistema de produção do Google, descrito por Bonawitz et al. (2019), treinou com **milhões** de dispositivos, selecionando clientes apenas quando carregando, conectados a redes sem franquia de dados e ociosos.

### 11.8.3 Internet das coisas e redes

Sensores industriais, veículos conectados e redes elétricas inteligentes geram dados na borda. Nguyen et al. (2021) revisam as aplicações em IoT: detecção de intrusão, manutenção preditiva, veículos e cidades inteligentes.

### 11.8.4 Finanças e seguros

Bancos e seguradoras têm obrigações de sigilo e dados complementares: o cenário clássico do aprendizado **vertical** (Yang et al., 2019), por exemplo, para avaliação de crédito e detecção de fraude entre instituições.

## 11.9 Regulação, ética e responsabilidade

### 11.9.1 Aprendizado federado não é anonimização

Um erro perigoso é achar que "os dados não saem, logo não há problema". Como vimos nos Capítulos 7 a 9, atualizações vazam informação, e modelos memorizam. Do ponto de vista jurídico, um modelo que memoriza dados pessoais **pode ser tratado como dado pessoal**, a depender da jurisdição e do caso.

### 11.9.2 Princípios de proteção de dados

A **LGPD** (Lei nº 13.709/2018), no Brasil, e o **GDPR**, na União Europeia, estabelecem princípios que se aplicam a projetos federados:

- **Finalidade:** o uso dos dados precisa ter um propósito claro e legítimo.
- **Minimização:** coletar e tratar só o necessário.
- **Transparência:** informar claramente o titular.
- **Segurança:** adotar medidas técnicas e administrativas.
- **Responsabilização:** poder demonstrar a conformidade.
- **Base legal** para o tratamento, como consentimento ou legítimo interesse.

Projetos de alto risco costumam exigir um **relatório de impacto à proteção de dados** (RIPD, no Brasil; DPIA, na Europa). Regulamentos de inteligência artificial, como o da União Europeia aprovado em 2024, acrescentam exigências conforme o risco do sistema.

:::atencao Atenção
Este livro **não é aconselhamento jurídico**. Antes de usar dados pessoais, consulte o encarregado de dados (DPO) e o jurídico da organização.
:::

### 11.9.3 Justiça (*fairness*)

Um modelo global pode servir **bem à maioria** e **mal a minorias**. Em aprendizado federado, pode favorecer clientes grandes ou com dados típicos. Duas propostas conhecidas:

- **Aprendizado federado agnóstico** (Mohri et al., 2019): otimiza o **pior caso** sobre misturas dos clientes, em vez da média.
- **q-FFL** (Li et al., 2020a): dá mais peso aos clientes com **maior perda**; um parâmetro *q* regula o quanto a justiça pesa sobre a média.

Meça sempre por cliente (como no Capítulo 6): média, pior cliente e percentil 10.

### 11.9.4 Incentivos e governança

- **Por que participar?** Se o modelo beneficia a todos, há tentação de "pegar carona". Mecanismos de incentivo e de **atribuição de valor** à contribuição de cada cliente são um problema aberto (Kairouz et al., 2021).
- **Governança:** em cross-silo, definir por contrato quem controla o modelo, quem pode usá-lo e o que acontece quando um participante sai.
- **Transparência e auditoria:** documentar dados, protocolos e riscos conhecidos (por exemplo, com fichas técnicas de modelo e de conjuntos de dados).
- **Impacto ambiental:** muitos clientes treinando consome energia. Compare com o custo do treino centralizado.

## 11.10 Lista de verificação de um projeto federado

:::memorize Antes de começar um projeto federado
1. **Necessidade:** os dados realmente não podem ser centralizados? Há alternativa mais simples?
2. **Cenário:** cross-device ou cross-silo? Horizontal ou vertical?
3. **Dados:** quão heterogêneos? Há desbalanceamento entre clientes?
4. **Modelo:** cabe nos clientes? Vale usar adaptadores ou modelos menores?
5. **Comunicação:** qual orçamento por rodada? Compressão necessária?
6. **Privacidade:** modelo de ameaça definido? DP, agregação segura?
7. **Robustez:** risco de clientes maliciosos? Agregador robusto?
8. **Avaliação:** testes locais por cliente, com média, pior cliente e percentil 10.
9. **Legal e ético:** base legal, RIPD, governança, justiça, auditoria.
10. **Operação:** monitoramento, versão do modelo, atualização e retirada de participantes.
:::

## 11.11 Problemas em aberto

Kairouz et al. (2021) reúnem dezenas de problemas em aberto. Alguns dos mais relevantes:

- garantias de privacidade úteis **com poucos clientes**;
- **robustez** sem abrir mão da agregação segura;
- **heterogeneidade** extrema e **personalização** em escala;
- **modelos de fundação** federados: eficiência, memorização e avaliação;
- **justiça** e **incentivos** em sistemas reais;
- **benchmarks** realistas, com dados e sistemas heterogêneos.

## 11.12 Resumo do capítulo

:::memorize O essencial do Capítulo 11
- Algoritmos baseados em **somas de estatísticas** (K-means, PCA) têm versões federadas **exatas**.
- Modelos de fundação pedem **ajuste eficiente** (adaptadores, LoRA): só *A* e *B* trafegam.
- A capacidade do adaptador (posto) deve casar com a tarefa.
- Frameworks: Flower, TFF, PySyft, FATE, FedML, FLARE, OpenFL. Escolha conforme o cenário.
- Aplicações: saúde, celulares, IoT e finanças.
- Federado **não é anonimização**: respeite LGPD, GDPR, finalidade e minimização.
- Justiça, incentivos e governança são parte do projeto, e não um detalhe.
:::
