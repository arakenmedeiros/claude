## 4.1 Cada cliente é de um jeito

Imagine uma rede de pizzarias. A unidade da praia vende muita pizza de camarão. A do centro financeiro vende mais pizza vegetariana. A do bairro universitário vende pizza grande e barata.

Se cada unidade ajusta a receita com base **só no seu movimento**, as receitas ficam bem diferentes. Se a matriz tirar a média das três, a pizza resultante pode agradar a **ninguém**.

É o problema dos **dados não-IID** (Kairouz et al., 2021).

:::cotidiano No seu dia a dia
Seu celular e o do seu vizinho têm dados bem distintos: vocês escrevem de forma diferente, usam outros aplicativos e falam sobre outros assuntos. Um teclado inteligente que aprenda com todos precisa lidar com essas diferenças.
:::

## 4.2 O que é IID e não-IID

**IID** significa "independentes e identicamente distribuídos". Em palavras simples: todos os exemplos vêm da **mesma fonte**, como se tivessem sido sorteados de uma única urna.

Em aprendizado centralizado, costumamos embaralhar os dados e assumir IID. No federado, isso quase nunca vale. Cada cliente tem sua própria "urna".

Formalmente, cada cliente *k* tem uma distribuição de probabilidade *P_k(x, y)*. Os dados são **IID entre clientes** se *P_k* é a mesma para todos. Caso contrário, são **não-IID**.

Uma distribuição conjunta pode ser lida de dois modos:

$$ P(x, y) = P(y) · P(x | y) = P(x) · P(y | x) $$

Em palavras: *P(y)* diz quão comum é cada rótulo; *P(x | y)* diz como são os atributos de cada rótulo; *P(x)* diz como são os atributos em geral; *P(y | x)* diz qual rótulo costuma acompanhar cada atributo. Cada fatia pode variar entre clientes, e isso gera tipos diferentes de heterogeneidade.

## 4.3 Os tipos de heterogeneidade

Kairouz et al. (2021) e Li et al. (2022) organizam os casos mais comuns.

| Tipo | O que muda entre clientes | Exemplo do dia a dia |
|---|---|---|
| **Rótulos** (*label skew*) | *P(y)*: a frequência de cada classe | Um hospital oncológico vê mais tumores do que uma clínica de rotina |
| **Atributos** (*feature skew*) | *P(x)*: como os dados "se parecem" | Fotos tiradas por câmeras diferentes, caligrafias diferentes |
| **Quantidade** (*quantity skew*) | *n_k*: tamanho do conjunto local | Um usuário muito ativo e outro que usa pouco o aplicativo |
| **Conceito** (*concept shift*) | *P(y \| x)*: o mesmo dado, outra resposta | "Bom" para um cliente é "regular" para outro |

![f4_tipos](Figura 4.1 — Quatro tipos de heterogeneidade. Nas fatias de rótulos, atributos e quantidade, os clientes diferem em quem são e quantos são. No conceito, os mesmos pontos recebem rótulos diferentes.)

:::saibamais Saiba mais
Na prática, os tipos se misturam. Um hospital pequeno de uma cidade do interior pode ter poucos dados (quantidade), pacientes mais velhos (atributos) e mais casos de certa doença (rótulos), tudo ao mesmo tempo.
:::

## 4.4 Como simular dados não-IID

Para estudar o problema, precisamos de dados com heterogeneidade **controlada**. Há duas receitas muito usadas.

### 4.4.1 Shards (fatias por classe)

McMahan et al. (2017) ordenam os exemplos por classe, cortam em pedaços (*shards*) e entregam poucos pedaços a cada cliente. Se cada cliente recebe **um** pedaço, ele vê **uma única classe**: o caso extremo.

### 4.4.2 Dirichlet

A distribuição de **Dirichlet** sorteia proporções que somam 1. Para cada classe, sorteamos como ela será repartida entre os clientes. Um parâmetro **α** (alfa) controla o grau de heterogeneidade (Li et al., 2022):

- **α grande** (por exemplo, 100): repartição quase uniforme, ou seja, dados quase IID.
- **α = 1**: heterogeneidade moderada.
- **α pequeno** (por exemplo, 0,1): cada classe se concentra em poucos clientes, ou seja, dados muito não-IID.

![f4_dirichlet](Figura 4.2 — Proporção de cada classe (colunas) em cada cliente (linhas), para três valores de α. Quanto menor o α, mais concentrada é a distribuição.)

Vamos medir o efeito com a `fedlib`.

```python
import numpy as np
from fedlib import *

Xtr, Xte, ytr, yte = carregar_digits()
print(f"{'alfa':>6} | classe dominante média | classes por cliente (>= 5 exemplos) | tamanhos")
for alfa in (100, 1.0, 0.1):
    partes = particao_dirichlet(ytr, k=10, alfa=alfa, seed=0)
    dominante, n_classes = [], []
    for p in partes:
        cont = np.bincount(ytr[p], minlength=10)
        dominante.append(cont.max() / max(cont.sum(), 1))
        n_classes.append(int((cont >= 5).sum()))
    print(f"{alfa:>6} | {np.mean(dominante):>22.2f} | {np.mean(n_classes):>36.1f} | {sorted(len(p) for p in partes)}")
```

Observe: com α = 100, cada cliente vê quase todas as classes. Com α = 0,1, cada um vê poucas, e os tamanhos ficam muito desiguais.

## 4.5 Por que o não-IID atrapalha?

### 4.5.1 Deriva dos clientes

Cada cliente treina com seus dados e caminha para o **seu** mínimo local. Quanto mais passos locais, mais longe do mínimo global ele chega. Ao tirar a média, o modelo resultante pode ficar longe do ótimo (Karimireddy et al., 2020). Esse fenômeno é a **deriva dos clientes** (*client drift*).

Um exemplo extremo ajuda. Dois clientes, com mínimos locais diferentes. Se cada um treinasse **até convergir**, a média dos modelos seria a média dos dois mínimos locais, que **não é** o mínimo da função global. Wang et al. (2020b) chamam isso de **inconsistência do objetivo**: com muitos passos locais e quantidades diferentes de passos, o FedAvg converge para um ponto que **não minimiza** o objetivo desejado.

![f4_deriva](Figura 4.3 — Em um caso de brinquedo, com muitos passos locais, o FedAvg estaciona na média dos mínimos locais (losango), e não no mínimo global (estrela).)

### 4.5.2 Outros efeitos

- **Convergência mais lenta e instável.** A curva de acurácia oscila, sobretudo quando poucos clientes participam de cada rodada.
- **Viés.** Clientes grandes dominam a média. Clientes pequenos ou "diferentes" ficam mal atendidos.
- **Difícil ajustar.** Hiperparâmetros que funcionam em IID podem falhar em não-IID.

![f4_curvas](Figura 4.4 — FedAvg com 20 clientes, poucos participantes por rodada (10%), 20 épocas locais e η = 0,3. Quanto mais heterogêneos os dados, mais lenta e instável é a curva. Média de 3 sementes.)

:::atencao Atenção
Com modelos simples e convexos, como a regressão logística, o efeito final costuma ser **moderado**: o modelo chega perto do ideal, mas **demora mais e oscila**. Em redes neurais profundas, as perdas costumam ser maiores. Interprete cada resultado dentro do seu contexto.
:::

## 4.6 Medindo a heterogeneidade

Antes de combater o problema, é bom medi-lo. Uma medida simples para rótulos é a **distância de variação total** entre a distribuição de classes de um cliente e a global:

$$ TV_k = (1/2) · Σ_c | p_k(c) − p(c) | $$

Ela vai de 0 (idênticas) a 1 (totalmente diferentes). Em palavras: é a fração dos exemplos que "estaria na classe errada" se quiséssemos transformar uma distribuição na outra.

Médias altas de *TV_k* indicam forte heterogeneidade de rótulos.

## 4.7 Algoritmos para dados heterogêneos

Vários algoritmos foram criados para reduzir a deriva. Três ideias são essenciais.

### 4.7.1 FedProx: uma "coleira" no cliente

O **FedProx** (Li et al., 2020c) adiciona ao erro local um termo que **penaliza o afastamento** do modelo global:

$$ F_k(w) + (μ / 2) · ‖ w − w_t ‖² $$

O hiperparâmetro *μ* ("mu") controla a força da coleira. Com *μ* = 0, volta-se ao FedAvg. Com *μ* grande, o cliente quase não sai do lugar. O gradiente do termo extra é *μ(w − w_t)*, e a `fedlib` já o suporta pelo argumento `mu`.

### 4.7.2 SCAFFOLD: corrigir a direção

O **SCAFFOLD** (Karimireddy et al., 2020) estima, para cada cliente, **quanto sua direção de descida difere da direção global**, e corrige cada passo local. Para isso, servidor e clientes mantêm **variáveis de controle**: vetores *c* (do servidor) e *c_k* (de cada cliente). O passo local vira:

$$ w ← w − η · ( g(w) − c_k + c ) $$

Em palavras: do gradiente do cliente, subtraímos sua tendência individual (*c_k*) e somamos a tendência global (*c*). Isso compensa a deriva, ao custo de **comunicar o dobro** de números por rodada, pois também se enviam as variáveis de controle.

### 4.7.3 FedNova: normalizar o esforço

Se um cliente dá 100 passos e outro dá 10, a média ponderada trata os dois como se tivessem contribuído igual. O **FedNova** (Wang et al., 2020b) **normaliza** cada atualização pelo número de passos locais antes de agregar, o que elimina a inconsistência do objetivo.

### 4.7.4 Outras ideias

- **Otimizadores no servidor:** FedAdam, FedYogi e FedAdagrad tratam a atualização média como um gradiente e usam métodos adaptativos (Reddi et al., 2021).
- **Personalização:** em vez de um modelo único, cada cliente fica com um modelo ajustado a si (Capítulo 6).
- **Agrupar clientes parecidos:** treinar um modelo por grupo (Capítulo 6).

| Algoritmo | Ideia | Custo extra | Quando ajuda |
|---|---|---|---|
| FedProx | Penaliza afastar-se de w_t | Quase nenhum | Dispositivos com esforço variável |
| SCAFFOLD | Corrige a deriva com variáveis de controle | 2× a comunicação; estado nos clientes | Forte heterogeneidade de rótulos |
| FedNova | Normaliza por número de passos | Quase nenhum | Quantidades de passos diferentes |
| FedAdam e afins | Otimizador adaptativo no servidor | Memória no servidor | Problemas mal condicionados |

## 4.8 Implementando o SCAFFOLD

Abaixo, uma implementação do SCAFFOLD (variante com "opção II" de atualização dos controles) com a `fedlib`. Salve o código como **`scaffold.py`**, ao lado da `fedlib.py`. Atenção ao ponto crítico: **clientes não sorteados mantêm seu *c_k***.

```python
import numpy as np
from fedlib import *

def scaffold(partes, X, y, Xte, yte, rodadas=40, epocas=10, eta=0.1, lote=32,
             frac=0.25, seed=0, classes=10):
    rng = np.random.default_rng(seed)
    W = np.zeros((X.shape[1], classes))
    c = np.zeros_like(W)                          # controle do servidor
    ck = [np.zeros_like(W) for _ in partes]       # controle de cada cliente
    historico = []
    for r in range(rodadas):
        m = max(1, int(round(frac * len(partes))))
        escolhidos = rng.choice(len(partes), m, replace=False)
        dW, dC = [], []
        for k in escolhidos:
            idx = partes[k]
            if len(idx) == 0:
                continue
            Xk, yk = X[idx], y[idx]
            w, passos = W.copy(), 0
            rk = np.random.default_rng(seed * 1000 + r * 50 + int(k))
            for _ in range(epocas):
                ordem = rk.permutation(len(yk))
                for i in range(0, len(yk), lote):
                    b = ordem[i:i + lote]
                    w -= eta * (gradiente(w, Xk[b], yk[b]) - ck[k] + c)   # passo corrigido
                    passos += 1
            ck_novo = ck[k] - c + (W - w) / (passos * eta)               # novo controle local
            dW.append(w - W)
            dC.append(ck_novo - ck[k])
            ck[k] = ck_novo
        W = W + np.mean(dW, axis=0)
        c = c + (len(dW) / len(partes)) * np.mean(dC, axis=0)
        historico.append(acuracia(W, Xte, yte))
    return W, historico
```

## 4.9 Comparando FedAvg, FedProx e SCAFFOLD

Agora o teste mais duro: **20 clientes**, cada um com **uma única classe** (*shards*), **10% de participação** por rodada, 20 épocas locais e η = 0,3. Três sementes.

```python
import numpy as np
from fedlib import *

from scaffold import scaffold      # o arquivo salvo na seção 4.8

Xtr, Xte, ytr, yte = carregar_digits()
cfg = dict(rodadas=40, epocas=20, eta=0.3, frac=0.1)
res = {"FedAvg": [], "FedProx (mu=0.1)": [], "SCAFFOLD": []}
for s in range(3):
    partes = particao_shards(ytr, k=20, por_cliente=1, seed=s)
    res["FedAvg"].append(fedavg(partes, Xtr, ytr, Xte, yte, seed=s, **cfg)[1])
    res["FedProx (mu=0.1)"].append(fedavg(partes, Xtr, ytr, Xte, yte, mu=0.1, seed=s, **cfg)[1])
    res["SCAFFOLD"].append(scaffold(partes, Xtr, ytr, Xte, yte, seed=s, **cfg)[1])

print(f"{'método':<18}{'rodada 10':>10}{'rodada 40':>10}{'oscilação (dp últ.10)':>24}")
for nome, hs in res.items():
    h = np.array(hs)
    print(f"{nome:<18}{h[:, 9].mean():10.3f}{h[:, -1].mean():10.3f}{h[:, -10:].std(axis=1).mean():24.3f}")
```

![f4_algos](Figura 4.5 — Acurácia por rodada com 20 clientes de uma classe cada, 10% de participação, 20 épocas locais e η = 0,3. O SCAFFOLD é mais rápido e estável; o FedProx não ajudou neste cenário.)

O que aprendemos:

- O **SCAFFOLD** foi claramente melhor: mais rápido e com menos oscilação.
- O **FedProx** com *μ* = 0,1 praticamente **não mudou** o resultado. Em modelo convexo e simples, a coleira traz pouco. Com *μ* grande, atrapalha: mais rigidez, menos progresso.
- Nenhum algoritmo vence em tudo: **teste no seu problema**.

:::dica Dica
Sempre compare algoritmos com **várias sementes** e as mesmas condições (mesmos clientes, mesmo número de rodadas). Uma diferença de 0,3 ponto percentual com uma única semente não prova nada.
:::
